# Implementation Summary — Sealed Door Prototype

## Scope Amendment — Controls HUD (2026-08-05)

Per `AgentCrew/inputs/approved_scope_amendment_controls_hud.md`, a small,
human-approved presentation enhancement. This does not reopen or reinterpret
the full feature plan; the door/interaction/progress logic already delivered
is unchanged.

### What Was Added

A compact, always-visible controls panel, `Canvas/ControlsHud`, generated by
`DoorPrototypeSceneBuilder.BuildControlsHud`. It is a background `Image` with
a single child `Text` element reading:

```
WASD - Move
Hold E - Open Door
Moving or taking damage
cancels the opening attempt
[Debug/Test] K - Take Damage
```

### Verifying Labels Against the Actual Implementation

Before writing any label, the actual input code was inspected rather than
assumed:
- `PlayerMovement.cs` reads `Keyboard.current.wKey/aKey/sKey/dKey` — confirms
  "WASD - Move".
- `PlayerInteractionController.cs` has `[SerializeField] private Key
  interactKey = Key.E;` and calls `BeginInteraction`/`EndInteraction` on
  press/release — confirms "Hold E - Open Door".
- `PlayerInteractionController.OnPlayerMoved()` and `HandleDamaged` both call
  `EndInteraction()` — confirms the interruption-rule line.
- `DebugDamageControl.cs` has `[SerializeField] private Key damageKey =
  Key.K;` and is explicitly commented as a testing/demo affordance, not a
  combat system. The HUD shows this binding prefixed with `[Debug/Test]` so it
  is never mistaken for a normal player ability, matching the amendment's
  requirement and the existing "DEBUG: Take Damage (K)" button label already
  in the scene.

### Design Decisions

- **No new runtime script.** The HUD is static, build-time-authored UI with
  no per-frame state to bind (unlike the prompt/progress indicator, which
  track `DoorInteractable` state) — a `MonoBehaviour` would add a component
  with no behavior. This keeps the addition minimal per `CLAUDE.md`'s
  "small focused components" guidance.
- **Separate object, not merged into existing UI.** `ControlsHud` is a
  sibling of `InteractPrompt` and `ProgressFill` under the same `Canvas`, not
  nested inside either, so it cannot be hidden or resized by their state
  changes and stays independently positioned.
- **Placement.** Anchored to the top-left corner (`anchorMin`/`anchorMax` =
  `(0,1)`, offset `(16, -16)`), it cannot overlap the bottom-center prompt
  (`anchorY 0.2`), the bottom-center progress bar (`anchorY 0.12`), or the
  bottom-left debug button (`anchor (0.02, 0.02)`).
- **Idempotency comes for free from the existing architecture.** `Canvas` is
  already in `DoorPrototypeSceneBuilder.KnownRootNames` and is fully
  destroyed and rebuilt from scratch on every run of `BuildUI`, so
  `ControlsHud` — like `InteractPrompt` and `ProgressFill` before it — cannot
  be duplicated by re-running the builder. No new duplication-guard logic was
  needed.
- **Built-in resources only.** The panel background reuses the same
  `UI/Skin/Background.psd` builtin-extra sprite already used for the
  progress-bar track; the label uses the same `LegacyRuntime.ttf` builtin
  font already used elsewhere in the scene. No new assets or packages.

### Files Changed

- `Assets/NoSafeCircle/DoorPrototype/Editor/DoorPrototypeSceneBuilder.cs` —
  added `BuildControlsHud`, called at the end of `BuildUI`.
- `Assets/NoSafeCircle/DoorPrototype/Tests/Editor/DoorPrototypeSceneBuilderTests.cs` —
  added three Edit Mode tests: HUD exists and is a distinct object from the

  added a reference to `Unity.InputSystem` so the new test can read the

No runtime gameplay files were changed; door timing, cancellation, and
progress logic are untouched.

## Targeted Repair — Progress Indicator Not Visually Updating (2026-08-05)

### Human-Reported Defect

From `AgentCrew/inputs/human_playtest_feedback.md`: the door opens correctly after
holding E for five seconds, but the visible progress bar does not visually
update while the interaction is in progress — it appears but never animates.

### Diagnosed Cause

The runtime binding in `DoorInteractionUI.Update()` (`progressFillImage.fillAmount
= door.Progress`) and the underlying `DoorInteractable.Tick`/`Progress` logic were
already correct. The defect was in scene generation: `DoorPrototypeSceneBuilder.BuildUI`
created the progress-fill `Image` with `type = Image.Type.Filled` and
`fillMethod = Image.FillMethod.Horizontal` but never assigned a `sprite`.
Unity's `Image.OnPopulateMesh` falls back to drawing a full, unfilled solid
rect whenever `sprite == null`, regardless of `type`/`fillMethod`/`fillAmount` —
so the bar always rendered as a static, fully-filled rectangle no matter what
`Progress` reported. Confirmed directly in the previously-generated
`DoorPrototype.unity` (the fill `Image` entry had `m_Sprite: {fileID: 0}` with
`m_Type: 3`, i.e. Filled with no sprite). This is exactly the kind of defect a
one-off manual Inspector fix (assigning a sprite by hand) would mask without
surviving a scene rebuild.

### Repair

`Assets/NoSafeCircle/DoorPrototype/Editor/DoorPrototypeSceneBuilder.cs`:
- The progress indicator is now two nested UI objects: a static "ProgressFill"
  background `Image` (sliced, using the built-in `UI/Skin/Background.psd`
  sprite, for a visible track) and a child "Fill" `Image` bound to
  `DoorInteractionUI.progressFillImage`.
- The "Fill" `Image` is assigned the built-in `UI/Skin/UISprite.psd` sprite
  (via `AssetDatabase.GetBuiltinExtraResource<Sprite>`, an Editor-only,
  engine-provided resource — no external package or imported asset), with
  `type = Filled`, `fillMethod = Horizontal`, `fillOrigin = Left`. With a real
  sprite present, `fillAmount` now actually drives visible fill geometry.
- No runtime script changes were needed — `DoorInteractionUI` and
  `DoorInteractable` were already correct; the fix is entirely in the
  generated scene configuration, so rebuilding the scene is sufficient and no
  manual Inspector step is required or relied upon.

### Automated Coverage Added

New `Assets/NoSafeCircle/DoorPrototype/Tests/Editor/` Edit Mode test assembly
(`NoSafeCircle.DoorPrototype.Tests.Editor.asmdef`, Editor-platform only,
referencing the runtime and Editor assemblies) with
`DoorPrototypeSceneBuilderTests.cs`:
- `Build_ProgressFillImage_HasSpriteAssignedSoFillAmountIsVisible` — runs the
  scene builder and asserts the generated `Canvas/ProgressFill/Fill` `Image`
  has a non-null `sprite`, `Image.Type.Filled`, and
  `Image.FillMethod.Horizontal`. This regresses directly on the defect: it
  would have failed against the pre-repair builder and fails again if the
  sprite assignment is ever dropped.
- `Build_RunTwice_DoesNotDuplicateProgressFillHierarchy` — runs the builder
  twice and asserts exactly one `ProgressFill` object exists under `Canvas`
  afterward, covering AC-11 idempotency for this specific UI element.

The existing five Play Mode tests in
`Tests/DoorInteractionPlayModeTests.cs` (completion, half-duration progress,
release/movement/damage cancellation) were not modified — the underlying
`DoorInteractable`/`PlayerInteractionController` logic they exercise was
already correct and is unaffected by this repair.

## Feature Implemented

The Sealed Door Prototype described in `AgentCrew/inputs/door_feature_brief.md` and approved in `AgentCrew/outputs/feature_contract.json`: a placeholder WASD player approaches a sealed door, holds E for a configurable, default-5-second uninterrupted duration to open it, with deterministic cancellation on release, movement, or damage, backed by an in-range prompt and a progress-fill UI element, and generated entirely through an idempotent Editor scene-builder command.

## Files Created

Runtime (`Assets/NoSafeCircle/DoorPrototype/`):
- `NoSafeCircle.DoorPrototype.asmdef` — runtime assembly, references `Unity.InputSystem` and `UnityEngine.UI`.
- `Scripts/DoorInteractable.cs` — owns `Duration`, `Progress` (0–1), `IsOpen`, `IsInteracting`, `IsPlayerInRange`; exposes `StartInteraction()`, `CancelInteraction()`, and a public `Tick(float deltaTime)` used both by its own `Update()` and directly by tests for deterministic time advancement. Owns the door's trigger-zone detection (`OnTriggerEnter`/`OnTriggerExit`) and notifies `PlayerInteractionController`.
- `Scripts/PlayerInteractionController.cs` — the sole gateway between input/physics and the door. Exposes `BeginInteraction()`, `EndInteraction()`, `OnPlayerMoved()`, `NotifyDoorInRange()`, `NotifyDoorOutOfRange()`. Reads `Keyboard.current` (new Input System) in `Update()` only to call the same public methods tests use directly. Subscribes to `PlayerHealth.Damaged` to cancel on damage.
- `Scripts/PlayerMovement.cs` — WASD movement via `CharacterController` and the new Input System; calls `PlayerInteractionController.OnPlayerMoved()` only when horizontal input is non-zero.
- `Scripts/PlayerHealth.cs` — minimal `TakeDamage(float)` plus a `Damaged` C# event; no death/respawn logic (out of scope).
- `Scripts/DoorInteractionUI.cs` — binds `DoorInteractable.IsPlayerInRange`/`IsOpen` to a prompt GameObject's active state and `Progress` to an `Image.fillAmount`.
- `Scripts/DebugDamageControl.cs` — clearly-labeled testing/demo affordance: pressing K or clicking the "DEBUG: Take Damage" button calls `PlayerHealth.TakeDamage`. Explicitly documented as not a combat system.

Editor:
- `Editor/NoSafeCircle.DoorPrototype.Editor.asmdef` — Editor-only assembly referencing the runtime assembly.
- `Editor/DoorPrototypeSceneBuilder.cs` — `No Safe Circle/Build Door Prototype Scene` menu command. Opens the existing `DoorPrototype.unity` if present (or creates a new empty scene), destroys any existing root objects matching a fixed set of known names, then rebuilds the entire hierarchy from scratch and saves. All cross-object serialized references (door visual/blocker, UI bindings, controller/health links, debug button listener) are wired via `SerializedObject` / direct property assignment, not manual Inspector work. Also builds `Canvas/ControlsHud`, a static always-visible controls panel (see the Scope Amendment section above).

Tests:
- `Tests/NoSafeCircle.DoorPrototype.Tests.asmdef` — Play Mode test assembly referencing the runtime assembly, `UnityEngine.TestRunner`, `UnityEditor.TestRunner`, and NUnit.
- `Tests/DoorInteractionPlayModeTests.cs` — five `[UnityTest]` cases (see Test Instructions below).
- `Tests/Editor/NoSafeCircle.DoorPrototype.Tests.Editor.asmdef` — Editor-platform-only Edit Mode test assembly, added during the progress-indicator repair (see below), referencing the runtime and Editor assemblies, and `Unity.InputSystem` (added for the Controls HUD tests).
- `Tests/Editor/DoorPrototypeSceneBuilderTests.cs` — Edit Mode tests that run the scene builder and assert its generated UI configuration: progress-fill sprite/idempotency (progress-indicator repair) and Controls HUD presence/text/idempotency (Controls HUD scope amendment).

Not created by this agent: `Assets/NoSafeCircle/DoorPrototype/Scenes/DoorPrototype.unity`. Per the contract, this file must only be produced by running the menu command inside the Unity Editor and is intentionally not hand-authored.

## Design Decisions

- **Time advancement is decoupled from frame rate.** `DoorInteractable.Tick(float deltaTime)` is public specifically so Play Mode tests can advance the 5-second timer deterministically (e.g., 100 × 0.05s steps) instead of waiting on real wall-clock time via coroutines.
- **Trigger detection lives on the door, not the player**, matching the brief's "sealed door GameObject with a trigger-based interaction range zone" and giving `DoorInteractionUI` a single natural source (`DoorInteractable.IsPlayerInRange`) for the prompt.
- **`PlayerInteractionController` is the only class that touches `Keyboard.current`.** All state transitions (`BeginInteraction`, `EndInteraction`, `OnPlayerMoved`) are public methods independent of input polling, satisfying AC-6; the Play Mode tests never touch the Input System.
- **The player's `CharacterController` doubles as its trigger-detection collider** (it derives from `Collider`), so no extra collider component is needed on the player for range detection.
- **The debug damage control is a single small script** (`DebugDamageControl`) wired to both a keypress (K) and a UI button via `UnityEventTools.AddPersistentListener`, kept intentionally minimal and explicitly commented as a testing/demo affordance only.
- **Scene-builder idempotency** is achieved by destroying a fixed list of known root GameObject names before every rebuild rather than trying to patch an existing hierarchy in place — simpler to reason about and guarantees no duplicates or stale references across repeated runs.

## Scene-Generation Instructions

1. Open the project in Unity `6000.1.8f1` and let it finish compiling the new scripts.
2. In the menu bar, run **No Safe Circle → Build Door Prototype Scene**.
3. The command creates/replaces `Assets/NoSafeCircle/DoorPrototype/Scenes/DoorPrototype.unity` containing: a floor plane, two flanking wall cubes forming a doorway gap, a door root (trigger zone + visual/blocking door cube), a player capsule with `CharacterController`, a directional light, a camera, a Canvas with an interaction prompt, a progress-fill image, a top-left Controls HUD panel, an `EventSystem` using `InputSystemUIInputModule`, and a labeled "DEBUG: Take Damage (K)" button.
4. Re-running the command from any state (empty project, already-built scene, or a manually edited copy) is safe — it will rebuild the known objects fresh and leave everything else in the scene untouched.

## Test Instructions

1. Open **Window → General → Test Runner**, switch to the **Play Mode** tab.
2. Run `NoSafeCircle.DoorPrototype.Tests.DoorInteractionPlayModeTests`. It does not require the generated scene — each test builds its own minimal `DoorInteractable`/`PlayerInteractionController`/`PlayerHealth` GameObjects.
3. Covered cases: completion after full duration, progress ≈0.5 at half duration, release cancels, movement cancels, damage cancels.

## Known Limitations

- The player has no gravity/jump; a small constant downward `CharacterController.Move` offset keeps it grounded on the flat floor, which is sufficient for this prototype's flat single-room layout.
- The door "opens" by deactivating its visual/blocking cube rather than playing an open animation; this satisfies "permits passage" (AC-12) without adding animation systems, which were not requested.
- Walls are two plain cubes flanking the doorway for visual context only; there is no enclosed room.
- Scene visual/interaction correctness (AC-7, AC-8, AC-10, AC-11, AC-12) requires manual verification in the Unity Editor, which this agent cannot perform.

## Excluded Systems Confirmation

No enemy AI, NavMesh, ranged enemies, Frost Field, Force Wave, Fireball, door locking/durability/breaking, multiple rooms, custom art/imported assets, runtime generative AI, or Unity MCP integration were implemented. `Packages/manifest.json` and `ProjectSettings/` were not modified — no external packages were added.

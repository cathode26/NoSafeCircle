Do not enable the proposed bundle as written. D2b requires a replacement design; D1, D2a, D3, D4, and D5 need specific changes before they preserve their claimed boundaries. The baseline does show repeated validation, but it does not establish the proposed savings or the claimed setup bottleneck.

**Ranked technical findings**

1. **P1 / STOP — D2b can carry an excluded task into a supposedly passing batch.** If candidate B is synchronized onto a tip containing A, B now contains A. After A's test fails, “discard batch and re-batch passing B” does not remove A from B's history/tree. Returning these mutated candidates to the ordinary path also leaks unlanded batch content or fails ancestry checks. A conflict, Source advance, stop or crash needs the same containment rule. Private construction from immutable original candidates is required; exclusion must rebuild from H with proof that the excluded contribution is absent. Task membership is not established by an ordered list alone.

2. **P1 / STOP — D2b's union API and parallel validation mechanics do not work as specified.** C:\nscrev\astra-design\Pipeline\AssistantControl\source_update.py:258–322 requires the actual manager.source HEAD to equal expected_source_commit, validates the record's source identity, and checks its source ancestry. After H1 is constructed in an ephemeral tree while real Source remains H, synchronizing a second candidate “onto H1” through this unchanged API refuses. Repointing manager.source changes ownership and registry identity; it is not equivalent reuse. Then all P validations are directed at one writable Unity project. The test runner deletes Library\ilpp.pid before launching Unity (C:\nscrev\astra-design\Pipeline\Testing\run_unity_tests_clean.ps1:411–418), so parallel use can remove another invocation's marker; Unity locking/import activity and churn checks conflict. Use independent owned clones of exactly Hn or one serial project lease. The existing post_crew workflow also binds a task's own checkout and candidate, not a free-form union worktree.

3. **P1 / STOP — D3's exact context_paths comparison does not prove unchanged proposal inputs.** C:\nscrev\astra-design\Pipeline\TaskDecomposition\context_builder.py:289–300 drops absent exclusive-resource and bootstrap paths, and even catches bootstrap path errors. An absent path appearing later cannot be checked from that list. More fundamentally, Claude is explicitly told that other repository files may be inspected for dependencies (C:\nscrev\astra-design\Pipeline\AgentRuntime\providers\claude_code.py:449–460); Read/Glob/Grep capabilities are not restricted to context_paths. A provider can read Assets/X.cs outside the list, base a proposal on it, and have that file change before apply while the proposed proof passes. Directory searches and absence observations require directory/predicate membership identity, not only hashes of files returned. The graph neighborhood includes dependents, siblings and a catalog; existing broad graph guards cover these and must not be narrowed.

4. **P1 / STOP — D1's “faster but cannot be wrong” claim lacks a trust boundary.** An ignored Library can contain compiled assemblies, importer artifacts and PackageCache contents that affect validation. Three committed files are a compatibility hint, not a proof of those bytes or all their inputs. Same file count and total bytes accept same-length corruption or substitution. A success receipt can also contain result.status = validation_failed, as NSC-1143 demonstrates: only authenticated passing validation of the exact producing candidate is eligible to publish a seed. Unity's dependency tracking depends on valid declared inputs and import behavior; it is not authentication of an arbitrary copied directory. [Unity 6.1 refresh documentation](https://docs.unity3d.com/6000.1/Documentation/Manual/AssetDatabaseRefreshing.html) and [Unity's import determinism guidance](https://docs.unity3d.com/jp/current/Manual/build-deterministic-assets.html) support this limitation.

5. **P1 / STOP — D5's action allowlist is not a complete delegate-safe mutation boundary.** Startup reconciliation, stale-stop archival and harvest run before allowed_actions is checked (C:\nscrev\astra-design\Pipeline\AssistantControl\graph_controller.py:1699–1724). Generic reconciliation can adopt, stop or quarantine retained jobs; decomposition cleanup can inspect/remove its owned container. Allowing a delegate to launch setup jobs does not automatically authorize it to harvest/stop arbitrary other kinds. A delegated setup child can also finish and publish a checkout after handoff. Define capability-scoped launch/adopt/harvest/stop and the durable handoff owner; reaching wait_job does not end all mutation.

6. **P1 / STOP — D2a is a multi-phase mutation, not just a process relocation.** Synchronization writes a pre_ff journal, fast-forwards the owned task checkout, rewrites candidate lineage, clears approval and removes worker/scope/launch fields (C:\nscrev\astra-design\Pipeline\AssistantControl\source_update.py:135–164,258–391). A death after FF but before record finalization or validation changes what a retry must authenticate. The existing background receipt binds request and process identity, not a semantic proof of the new target/result transition (C:\nscrev\astra-design\Pipeline\AssistantControl\background_jobs.py:644–662,1494–1537,2306–2320). Child-side record writes occur before harvest. Rejecting a receipt after a bad mutation is insufficient.

Four Git-only children are not four parallel clones under the current lock. Copying a large Library inside prepare lengthens the same critical section. “Frees Source lane” is false for sync's lock duration; at best it frees some scheduling CPU time. **D1 — required design changes, tests, dependencies**

Identity: keep exact commit/tree, policy, filter, platform, Unity executable/version and XML/log/runner identities. Treat seed identity as an additional execution input. The key must use the actual producing validated candidate, not its old record.source_commit: a task may change ProjectSettings or Packages. Define canonical structured hashing with path names and explicit missing-file representation. Include editor revision, host/architecture and active build target; account for ProjectSettings, scripting defines, assembly definitions, native plugins, importer/postprocessor code, Assets/.meta GUIDs, embedded/local packages and resolved package content. A broad key may deliberately permit invalidation/reimport across asset changes, but must not be advertised as sufficient proof of compatibility.

Unity tracks static and dynamic dependencies including platform and importer/global state. Custom importers must correctly declare dependencies; cold and warm behavior can differ when they do not. A whole Library is broader than Unity's documented imported-asset cache. The correctness gate is cold-versus-seeded equivalence for the supported environment and representative fixtures, with exact test discovery, outputs, GUID resolution and generated content checked. A three-file key and a clean Git status cannot establish universal equivalence.

Ownership: obtain a lease covering producing checkout, Unity process tree and population until publication; no active worker, importer or validation may write meanwhile. Absence of ilpp.pid is neither proof of process death nor an atomic lease. Keep immutable original input hashes and per-file cache digests. Serialize competing publishers by key; manifest-last in staging plus atomic rename is necessary but does not resolve two winners, manifest forgery, later cache modification or path redirection. Validate canonical paths and reject reparse points, symlinks/junctions and escaping entries at every copy/delete boundary. Define count/size over the filtered published set. [Robocopy's documented exit codes](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/robocopy) require treating codes >=8 as failures; success codes alone do not replace content verification.

Fail-closed: create into an exclusively owned disposable stage. On failure, prove the entire partial seed was removed before permitting cold validation. If removal fails or ownership changes, block instead of calling the project cold. Do not overwrite an existing Library during refresh without a separate transaction. Keep evidence outside the cache. Do not import producer receipts as consumer validation. Existing manifest reuse must still authenticate exact candidate/tree/policy and must be bypassed in measurement trials that intend to execute Unity.

Timing: an empty root cache cannot help checkouts already prepared before the first successful validation publishes it. Here all four initial implementation checkouts were prepared by +25.426 s, long before a successful focused validation. Later child preparation also needs a happens-before analysis. Eight prepared tasks do not imply eight seed hits. Measure copy, manifest hashing, cache publication, disk bytes, queue waits, imports and Unity execution together. Seeding an irrelevant decomposition snapshot would add disk/lock cost without Unity benefit.

Required failing-before tests:

- D1-T1: same-size/count altered DLL, PackageCache file or database entry is refused; truncated/incomplete manifest and missing/extra files leave no usable partial seed.
- D1-T2: producing candidate changes each key input after its base Source; publishing under the base key is rejected. Exercise editor revision, build target, scripting define, local/embedded package, .asmdef, .meta/GUID and importer changes.
- D1-T3: two publishers, writer starts during copy, Unity exits with a surviving child, absent/stale ilpp.pid, stop before/after manifest and rename; exactly one authenticated immutable entry, no stolen checkout ownership.
- D1-T4: reparse-path substitution, cache outside approved root, copy failure, disk exhaustion and failed partial cleanup; nothing outside the owned stage is removed, and incomplete cleanup blocks.
- D1-T5: admission/reserve, ordinary status, ignored status, refresh, sync and integration preserve their existing Git protections with a valid seed. Refresh operates on the existing project rather than replacing it.
- D1-T6: real cold/seeded identical-commit pairs discover the same tests and produce the same assertions, serialized outputs and GUID resolution; include a deliberately nondeterministic or undeclared-dependency importer to show the supported boundary. No pass laundering through cached validation manifests.

Before default: all above gates, authenticated cold/seeded equivalence evidence, producer/consumer provenance, corrupt-entry recovery, and net timing distributions including copy/hashing. **VINCENT DECISION:** choose supported cache scope, whether persistent cross-run caches are acceptable, disk retention/eviction budget, timing threshold (including the proposed under-45-second target), and how much cold verification to retain. **Safest position:** independent opt-in trial after instrumentation and cache trust/ownership changes; do not initially combine with D4's higher limits or background prepares.

**D2a — required design changes, tests, dependencies**

The foreground approved-but-stale path does not “need no validation and move nothing.” It mutates the candidate and clears approval, returning awaiting_human. Subsequent synthetic approval needs passing facts for the new commit; real tasks need the applicable renewed human review. Keep that property. Existing code's conservative refusal of a different expected Source is useful; do not silently replace the ticket's target with whichever HEAD exists when a queued job eventually runs.

Define a ticket transition C0 at base H0 -> merge Cs onto pinned H -> validation of Cs. Bind original candidate/tree, crew provenance/run/config, checkout/root/branch, task contract, target Source branch/commit/tree, validation policy/filter/platform, operation generation and resulting Cs/tree/merge-parent proof. State-changing APIs must authenticate this ownership before mutation, not just at launch/harvest. Separate “Source moved before sync” from failed tests. Source may advance after sync: Cs remains a valid historical result, but cannot be approved/landed as current without the ordinary freshness proof.

Use the same lock order as existing mutators and hold Source locks only for the sync phase, never the Unity validation. Shortening global critical sections needs an explicitly reviewed prepare/commit protocol, not removal of guards. A per-task lease must exclude human decisions, refresh, other syncs and worker launches while the child owns the transition, or these actions must fail against the exact owned phase. Existing one-controller planning is not sufficient protection for direct commands.

Required failing-before tests:

- D2a-T1: forged wrong target, Source branch, candidate, contract, policy, checkout or generation is refused before mutation and at result adoption; authenticate the receipt's resulting merge and facts against the durable sync operation.
- D2a-T2: Source moves while queued, while sync holds its lock, immediately after sync, during Unity and before harvest. No automatic target substitution; stale historical validation cannot authorize a new tree.
- D2a-T3: terminate at staging creation, pre_ff journal, checkout FF, record finalization, validation publication and receipt publication. Recover the same operation exactly once or block with preserved evidence; never auto-relaunch a dead ticket into a second mutation.
- D2a-T4: approved candidate sync clears old approval/facts and requires fresh validation/review; old human approval can never attach to Cs.
- D2a-T5: four queued syncs plus simultaneous harvest/integration/stop, with one sync deliberately >10 seconds; no deadlock, duplicate writer, controller-wide timeout failure or kill of unrelated processes.
- D2a-T6: human decision or revised candidate arrives before result persistence; latest state survives. Equivalence comparison to foreground must normalize UUIDs, staging paths, timing and process-specific metadata, then compare semantic lineage and facts—not demand byte identity except timestamps.

Before default: retained crash-recovery transcripts for every phase, exact ticket-to-result proof, lock contention/stop latency measurements and successful stale-approved regression. **VINCENT DECISION:** whether the measured responsiveness benefit warrants this added lifecycle and retry policy. **Safest position:** after instrumentation and mutation leases, at background limit 4, independently of D1/D3/D5.

**D2b — replacement design required**

The existing exact-tree argument is valid only within its scope: for an approved exact candidate C, Source H is its ancestor, merge --ff-only advances Source to C, and the committed tree equals tree(C). ReviewGate also preserves pre-existing Source local edits; committed-tree equality does not claim the entire live working directory is byte-equal to the validation checkout. Its before/after branch/ref/local-edit checks and --no-overwrite-ignore are essential (C:\nscrev\astra-design\Pipeline\AssistantControl\review.py:209–300).

Batch formation's “candidate facts bind H's tree” is wrong: ordinary facts bind each candidate C_i and tree(C_i), not Source H's tree. Validation on H plus a candidate is not the same as validation of H itself. A new batch must prove every intended contribution is represented in Hn and every required task policy runs against Hn; before-batch validations cannot be recycled as union facts. Requiring members to have already validated individually before union validation also adds P validations to the first successful batch, undermining the advertised count unless the design changes formation criteria.

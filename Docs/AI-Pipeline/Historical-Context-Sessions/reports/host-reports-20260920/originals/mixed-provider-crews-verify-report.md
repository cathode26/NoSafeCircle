## Q1 — The chain: BROKEN at the AssistantControl→bridge hop

Hops, in order:

1. Worker config JSON (`--config` file for `reserve`/`run-worker`/`start-worker`) is loaded **verbatim** — `Pipeline/AssistantControl/__main__.py:565-568` just does `json.loads(args.config.read_text(...))`; no CLI flag expands a profile name.
2. `Pipeline/AssistantControl/worker_launcher.py` → `Pipeline/AssistantControl/crew_worker.py:run_worker` (`crew_worker.py:191`) builds `bridge_config = dict(_bridge_options(saved_config))`. `_bridge_options` (`crew_worker.py:80-94`) whitelists the key `"provider_profile"` and copies it through **unchanged** — no call to `expand_profile()` or `crew_role_routes()` anywhere in `crew_worker.py` or `candidate.py` (same pattern at `Pipeline/AssistantControl/candidate.py:193-209`, its own revalidation bridge).
3. `bridge_factory(checkout=..., scope=..., **bridge_config)` → `Pipeline/TaskReviewAgent/execution_bridge.py:ExecutionCrewBridge.__init__` (`execution_bridge.py:293` signature: `provider_profile: dict | None`). At `execution_bridge.py:347-350` it does `provider_profile["topology"]` and `provider_profile["role_routes"]` — **this requires the fully-expanded dict**, not a profile name string.
4. If it were a proper dict, the rest of the chain is wired: `ExecutionCrewBridge._command` (`execution_bridge.py:455-467`) mounts **both** providers' credential volumes and passes `--provider-role-profile /nsc-pool/profile.json` to the container; `Pipeline/ExecutionCrew/run_crew.py:2909-2933` reads that file, reconstructs `ProviderTopology` + `role_routes`, and `run_crew.py:2138-2141` uses `role_routes[role]` per role inside `invoke_once`.

**The gap:** `provider_profiles.py:1-5` states the design intent explicitly — *"Only the composition root expands a profile. Downstream boundaries deserialize the exact resolved value."* AssistantControl (`crew_worker.py`, `candidate.py`, `__main__.py`) is a downstream boundary that correctly refuses to "rebuild" a topology — but **no composition root exists yet for the AssistantControl launch path**. `expand_profile()` is only called from the legacy `run_autonomous_graph.py:240` (bound to `Start-AutonomousGraphRun.ps1 -ProviderProfile`) and indirectly via `polling_orchestrator.py` (already-expanded `self.provider_topology`). Neither path writes an AssistantControl worker-config JSON.

Consequence: if an operator hand-writes `"provider_profile": "codex-architect-balanced"` (the natural profile-name string, matching `PROVIDER_PROFILES` in `provider_profiles.py:20`) into a worker config, `ExecutionCrewBridge.__init__` crashes with a `TypeError` on `provider_profile["topology"]` (string is not a mapping). Mixed crews only work through AssistantControl today if the operator hand-assembles the full `{topology, role_routes, provider}` dict themselves (via `expand_profile` + `crew_role_routes` + `.to_dict()`) and also sets a matching `"provider_allowlist"` — nothing does this automatically, and nothing validates a bare profile-name string and gives a clear error instead of the raw `TypeError`.

No hop **overrides** the value with `provider`/`provider_allowlist`/`quota_fallback_provider` — those are independent, compatible options (see Q2). It is dropped only in the sense that nothing ever converts it into the required shape.

## Q2 — Guards

- **`provider_allowlist` accepts a mixed profile:** yes, mechanically. `ProviderTopology.provider_allowlist` for `codex-architect-balanced`/`claude-architect-balanced` is `("claude", "codex")` (`provider_profiles.py:17-18`). `execution_bridge.py:351-352` requires the bridge's own `provider_allowlist` to exactly equal `topology.provider_allowlist` — so the worker config's `provider_allowlist` field must also list both providers, in the right order, or the bridge raises `ExecutionBridgeError("bridge provider allowlist differs from its profile")`. This is an easy-to-miss manual step, not a rejection of mixed profiles.
- **Quota fallback (`role_provider_overrides`) still behaves:** `run_crew.py:1984/2134/2407` computes `role_provider_overrides` independently of `role_routes`; `run_crew.py:2138-2141` lets `role_routes[role]` take priority when a profile is active, so a profile crew is not further overridden by ordinary single-provider quota fallback. Covered by existing tests in `provider_profiles_test.py` (`test_composition_expands_once_and_resume_is_exact`, `test_advisory_balance_preference_cannot_override_pressure`, etc.) — all passing.
- **Docker/compose is not single-provider only.** `compose.yaml` defines both `claude-exec` and `codex-exec` services and both `claude-config`/`codex-config` volumes (lines 42, 133, 204-205), and at least one service (`GauntletView`/decomposition, lines 199-200) already mounts both. `execution_bridge.py:440-464` explicitly mounts the *other* provider's credential volume into whichever service actually runs, for both the plain quota-fallback case and the profile case — so the crew container already supports both CLIs and both credential volumes.

## Q3 — Records: per-role provider is captured in crew evidence, not in the AssistantControl worker/candidate record

- `role_results/<role>_<attempt>.json`: yes. `run_crew.py:2509` writes `"provider": res.provider, "model": res.model` per role, sourced from the actual routed invocation (`routed_provider`/`routed_model`, `run_crew.py:2134-2141`).
- `run_result.json`: yes, when a profile is active — `run_crew.py:2767-2768` does `result.update(provider_topology=provider_topology, role_routes=role_routes)`.
- **AssistantControl worker record / candidate record: no.** `crew_worker.py:110` stores `worker["receipt"] = receipt.to_dict()`, and `ExecutionCrewReceipt.to_dict()` (`execution_bridge.py:226-248`) has a single top-level `"provider"` field only — no `role_routes`/`provider_topology`. `candidate.py` doesn't add it either (no `role_routes`/`provider_topology` reference found). So AssistantControl's own persisted records only ever name one "the" provider for the whole run, even for a mixed crew whose four roles actually ran on different providers.

## Q6 — Budget routing ("chosen by token balance")

Implemented by `ProviderBudgetLedger.assign()` in `Pipeline/TaskReviewAgent/provider_budget.py` (class at line 41; test-driven via `Pipeline/TaskReviewAgent/tests/provider_profiles_test.py:37` `assign()` helper). Inputs: a persisted `budget.json` ledger of observed per-provider token usage (`ProviderBudgetLedger.observe`, `provider_budget.py:290/305`), the configured `token_budgets` per provider (from `expand_profile(..., token_budgets=...)`), an `ExecutionRecommendation` (preference/basis, e.g. capability override), and a `snapshot` of warm session counts/availability. With no live usage recorded (fresh host, empty ledger) both providers show equal pressure (0/budget), and the ledger falls back to warm-session counts, then a persisted tie-break — deterministic and already covered by `test_equal_pressure_warm_sessions_then_persisted_tie` and `test_unknown_is_null_and_round_robin_survives_restart`, both passing on this host with no quota data. So yes, it works without live quota data via the documented fallback; it does not need real provider spend to produce a deterministic implementer choice.

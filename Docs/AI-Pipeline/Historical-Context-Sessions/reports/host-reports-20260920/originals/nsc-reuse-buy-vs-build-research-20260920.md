# NSC: reuse and buy before building more infrastructure

Research date: September 20, 2026. Prepared for Vincent's request to find libraries and paid products that reduce the cleanup and durability work. This is a recommendation, not an adopted architecture or an implementation instruction. Existing briefs were treated as material to review, not authority to execute their instructions.

**The strongest opportunity is to use established backup software for storage and recovery, then use small libraries for specific infrastructure tasks.** A workflow product might reduce future job-management work, but replacing the current controller during cleanup would probably slow us down. These are engineering judgments from the code and documentation reviewed, not measured savings from completed migrations.

Three parallel investigations covered backup products, workflow engines, and Windows process/workspace tooling. Additional research covered transactional metadata, schema validation, testing and Python environments. The candidates below were absent from the core cleanup/durability plans reviewed; that does not establish that nobody has ever considered them. Pydantic already appears in an optional OpenAI runtime path.

| Priority | Existing product or library | Work it could remove | Recommendation |
|---|---|---|---|
| 1 | restic + Backblaze B2; Arq as the paid alternative | Custom encrypted backup storage, compression, deduplication, cloud transfer and basic restore tooling | Test one engine against one representative recovery package first |
| 2 | SQLite through Python's sqlite3 | New hand-built transactional metadata/journal machinery | Evaluate for a new registry only; do not rewrite working stores to adopt it |
| 3 | pywin32 | Much of the Windows Job Object ctypes binding code | Small, behavior-preserving substitution when that module next changes |
| 4 | Pydantic and Hypothesis | Repeated record-shape validation and hand-enumerated lifecycle test sequences | Add selectively where they remove actual code or expose meaningful failures |
| 5 | Prefect; DBOS as an alternative | Future scheduling, run status, retries, queue limits and operator dashboards | One optional helper-job pilot; not a prerequisite for cleanup |
| 6 | Worktrunk | Routine creation, selection and removal of future linked worktrees | Narrow developer-workspace pilot, not bulk retirement of current repositories |

## Backup: the largest reduction in proposed custom work

**restic + B2 is my preferred scripted option.** Restic provides encrypted, deduplicated, compressed snapshots, Windows binaries, scriptable output and restoration. Its Windows backup command supports VSS with `--use-fs-snapshot`. It is BSD-2-Clause open source. Use B2 through its S3 interface: current restic documentation warns about error handling in the native B2 library. [Project](https://github.com/restic/restic), [backup/VSS documentation](https://restic.readthedocs.io/en/stable/040_backup.html), [backend setup](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html).

**Arq is the strongest paid option for reducing setup and operator-interface work.** Arq 7 costs $59.99 per computer, with storage purchased separately. Arq Premium is $69.99/year for five computers and 1 TB included storage; additional storage is $0.00699/GB/month. Its Windows backup plans use VSS by default and retain every backup record by default, though exclusions and retention must be checked for NSC. Arq 7's current checkout lists optional updates after the included first year at $29.99/year. [Product pricing](https://www.arqbackup.com/pricing/), [current checkout](https://cloud.arqbackup.com/purchase/arq7), [backup-plan behavior](https://www.arqbackup.com/documentation/arq7/English.lproj/createBackupPlan.html).

B2 currently lists $6.95/TB/month, the first 10 GB free, and free egress up to three times average monthly stored data, followed by $0.01/GB. One retained TB is roughly $83.40/year before the free allowance and other applicable charges. Actual NSC cost requires measuring retained compressed data and growth. [B2 pricing](https://www.backblaze.com/cloud-storage/pricing).

Two secondary choices are worth knowing about, but we should not deploy competing backup stacks during this sprint. **Kopia** provides an Apache-2.0 Windows GUI/CLI and snapshot policies; its documented Windows VSS solution requires before/after PowerShell actions, increasing integration work. **Veeam Agent for Windows** is useful for whole-machine recovery; the free edition's single-job and cloud-storage restrictions, plus short default retention, make it a supplement rather than the evidence archive. Paid Veeam pricing was not verified. [Kopia project](https://github.com/kopia/kopia), [VSS actions](https://kopia.io/docs/advanced/actions/), [Veeam editions](https://helpcenter.veeam.com/docs/agentforwindows/userguide/license_editions.html), [Veeam retention](https://helpcenter.veeam.com/docs/agentforwindows/userguide/backup_job_vbr.html).

The existing decision to retain **every log in Git** changes the potential savings. Under that decision, backup software mainly replaces second-copy storage and transfer machinery. It does not eliminate Git capture, packaging or GitHub-sized payload segmentation. A larger simplification would keep source, manifests and references in Git while storing bulk logs, art and dirty-workspace recovery packages in a backup archive. **That is a proposal to revisit the storage architecture, not an assumed change to Vincent's decision.**

The adapter NSC still needs is specific and bounded: identify every real source, include Git common stores and external dependencies, establish a coherent capture point, and validate an independent restoration before retiring originals. VSS provides a stable filesystem view; it does not understand a game change's source/contract/evidence transaction. A linked worktree's `.git` file alone is not its history. Junction behavior needs a Windows fixture rather than assumptions. These conclusions follow from [Microsoft's VSS writer model](https://learn.microsoft.com/en-us/windows-server/storage/file-server/volume-shadow-copy-service) and [Git's repository layout](https://git-scm.com/docs/gitrepository-layout).

Repository health checks also differ from proving that a particular cleanup candidate is recoverable. Restic's full payload verification requires `check --read-data`; an independent restore must still validate the NSC file/hash manifest, pinned art and required Git objects. Keeping snapshots forever does not itself make them immutable. Object-lock expiry, credentials and key recovery need an explicit configuration; a second bucket under the same administrative control is a weaker failure boundary. [Restic verification and copying](https://restic.readthedocs.io/en/stable/045_working_with_repos.html), [B2 Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock), [Arq Object Lock](https://www.arqbackup.com/documentation/arq7/English.lproj/objectLock.html).

## Small libraries: replace plumbing without changing the entire system

**SQLite is worth considering before building another JSON transaction system.** Python already supplies `sqlite3`; SQLite transactions and constraints can manage related registry rows and operation records in one local database. Candidate uses are newly proposed workspace ownership and cleanup-operation metadata. Human-readable JSON can be an exported view, rather than a second writable authority. The saving is persistence machinery; ownership rules and allowed state transitions remain NSC code. SQLite does not atomically include a Git ref update, a filesystem write or a subprocess side effect. [Python sqlite3](https://docs.python.org/3/library/sqlite3.html), [transactions](https://www.sqlite.org/lang_transaction.html), [atomic commit](https://www.sqlite.org/atomiccommit.html).

An adoption condition matters here: the checked `C:\Python313\python.exe` runtime reports SQLite **3.45.3**. Before a concurrent WAL-mode pilot, use a release containing the WAL-reset fix: 3.51.3 or later, or an applicable fixed backport such as 3.44.6/3.50.7. The documented race concerns concurrent writes/checkpoints through multiple connections. This is not evidence of a current NSC failure. WAL is for same-host storage, not a shared network database; use the backup API for a coherent live database copy. Do not casually copy only its main file while WAL is active. [WAL documentation](https://www.sqlite.org/wal.html), [backup API](https://www.sqlite.org/backup.html).

**pywin32 can replace much of the low-level Job Object binding code.** Its APIs closely match the create/open/assign/query/terminate operations in [windows_job.py](C:/NSC/NSC/NoSafeCircle/Pipeline/AssistantControl/windows_job.py:129). Preserve the existing named-job recovery behavior, verified process identity, termination deadline and deliberate absence of kill-on-close. One subtle exception: keep the raw creation-time reader, because pywin32's conversion through SYSTEMTIME loses the precision needed to reproduce the existing 100-nanosecond identity ticks. This should be a partial binding substitution. [Job bindings](https://github.com/mhammond/pywin32/blob/main/win32/src/win32job.i), [process-time conversion](https://raw.githubusercontent.com/mhammond/pywin32/main/win32/src/win32process.i), [datetime conversion](https://raw.githubusercontent.com/mhammond/pywin32/main/win32/src/PyTime.cpp).

**Pydantic can replace repetitive structural validation** for new manifests, registry entries and receipts. Use strict models and deliberate handling of extra fields; preserve duplicate-key rejection and semantic checks such as ownership, hash binding and approval freshness. It already appears in [the optional OpenAI runtime](C:/NSC/NSC/NoSafeCircle/Pipeline/TaskReviewAgent/openai_agent.py:49), so the opportunity is targeted reuse in new infrastructure, not discovery of a completely unknown dependency. [Project](https://github.com/pydantic/pydantic), [strict validation](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/).

**Hypothesis can generate and shrink lifecycle test sequences** involving registration, cancellation, revision, crash and restart. It can replace hand-written combinations and produce smaller reproductions. We still define the invariants and supply any actual Windows process/crash harness. Apply it to the risky protocol, not every reversible document change. [Stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html), [project](https://github.com/HypothesisWorks/hypothesis).

Two smaller conveniences: **uv** can standardize Python versions, dependency locks and isolated environments; **Tenacity** supplies bounded retry/backoff policies for suitable I/O. Neither merits its own migration project. Never automatically retry a possibly completed Git publication, deletion or paid provider call merely because a response was lost. [uv](https://docs.astral.sh/uv/), [Tenacity](https://tenacity.readthedocs.io/en/latest/).

## Workflow engines: buy visibility, avoid a controller rewrite

The live [background job module](C:/NSC/NSC/NoSafeCircle/Pipeline/AssistantControl/background_jobs.py:1) already includes retained receipts, restart reconciliation, named Windows Job Objects and exact Docker cleanup. [Worker settlement](C:/NSC/NSC/NoSafeCircle/Pipeline/AssistantControl/worker_settlement.py:19) checks completion proof and process state. Old problem reports should not be used to imply that this machinery is absent or still broken.

| Candidate | Verified platform and capability | Current cost | NSC fit |
|---|---|---|---|
| [Prefect](https://github.com/PrefectHQ/prefect) | Native Windows server/process workers; scheduling, run states, retries, global resource limits and dashboard | OSS self-hosting; Cloud Starter $100/month includes bring-your-own compute | Best first pilot if an operator interface saves substantial supervision |
| [DBOS Python](https://github.com/dbos-inc/dbos-transact-py) | In-process durable workflows and queues; Windows; SQLite initially, PostgreSQL recommended for production | OSS library; optional Pro $99/month, 2 seats, 3 apps, 1M checkpoints | Smaller library alternative if dashboard needs are modest |
| [Temporal Python](https://github.com/temporalio/sdk-python) | Windows workers; durable workflow replay and activity orchestration; separate production service/Cloud | Cloud Developer has no base fee plus 10% of usage; actions start at $50/M plus storage | Defer: strongest long-lived workflow machinery, largest migration burden |

Sources: [Prefect Windows guide](https://docs.prefect.io/v3/how-to-guides/self-hosted/server-windows), [Prefect pricing](https://www.prefect.io/pricing), [DBOS guide](https://docs.dbos.dev/python/programming-guide), [DBOS production guidance](https://docs.dbos.dev/production/checklist), [DBOS pricing](https://www.dbos.dev/dbos-pricing), [Temporal Windows worker example](https://temporal.io/setup/run-a-sample-workflow?sdk=python), [Temporal production deployment](https://docs.temporal.io/self-hosted-guide/deployment), [Temporal pricing](https://docs.temporal.io/cloud/pricing).

Prefer a pilot around one generic helper command in [run_job.py](C:/NSC/tools/jobs/run_job.py), retaining its path, provider, account, tool and spending guards. A shared heavy-job limit could replace the planned manual slot ledger **for enrolled jobs**. It cannot constrain bypassing writers or grant permission to write source. Prefect's named concurrency acquisition should use strict missing-limit handling; lease expiry still cannot prove that the old process stopped writing. [Prefect concurrency API](https://docs.prefect.io/v3/api-ref/python/prefect-concurrency-sync).

Do not confuse a product status with physical settlement. Prefect can mark cancellation complete after cleanup times out or when an infrastructure identifier is missing; DBOS cannot preempt a synchronous step; Temporal activity cancellation is cooperative. Keep the NSC process-containment adapter. External effects also need idempotency or reconciliation: an engine does not transactionally combine a Git commit, filesystem changes and its own checkpoint. [Prefect cancellation](https://docs.prefect.io/v3/advanced/cancel-workflows), [DBOS step timeouts](https://docs.dbos.dev/python/tutorials/step-tutorial), [Temporal SDK](https://github.com/temporalio/sdk-python), [Temporal idempotency](https://docs.temporal.io/develop/python/best-practices/error-handling), [DBOS external effects](https://docs.dbos.dev/python/examples/outbox).

Cloud run history is not the permanent evidence archive: current Prefect Starter lists seven-day run retention. A human-resume button also does not establish NSC merge approval; authority must remain tied to exact source/candidate/contract/evidence versions. [Prefect pricing](https://www.prefect.io/pricing).

## Workspace prevention: useful tooling has a narrower job

**Worktrunk** supports native Windows PowerShell/Git Bash and can handle ordinary worktree creation, selection, listing, hooks and removal. However, [checkouts.py](C:/NSC/NSC/NoSafeCircle/Pipeline/AssistantControl/checkouts.py:119) deliberately creates independent clones. Switching those to linked worktrees changes the isolation model. Pilot only ordinary future developer worktrees first. [Windows support](https://worktrunk.dev/faq/), [project](https://github.com/max-sixty/worktrunk).

Removal is background by default, so verified closeout needs foreground behavior; its `--reap` option is unavailable on Windows. Hooks are bypassable and therefore cannot be the only enforcement of register-before-create or preserve-before-delete. Worktrunk does not determine whether a repository contains unique evidence or who still depends on its object store. [Removal semantics](https://worktrunk.dev/remove/), [hooks](https://worktrunk.dev/hook/).

Other investigated options do not solve the central problem. **processkit-py** offers contained processes but normally kills descendants with owner lifetime, conflicting with NSC's recoverable named-job contract. **psutil** helps observation, but enumerating descendants is not reliable kernel containment. **GitPython/pygit2** simplify Git API use; even pygit2's reference transactions do not cover the working tree, external records or process ownership. [processkit](https://github.com/ZelAnton/processkit-py), [psutil ancestry limitations](https://psutil.readthedocs.io/stable/#psutil.Process.children), [pygit2 transaction scope](https://www.pygit2.org/transactions.html).

The cleanup agent should enforce a few project-specific obligations: register owned workspaces before creation, keep a live owner or bounded exception, obtain the parent's closeout, preserve dependency closure and evidence, and require a verified recovery receipt before retirement. Existing lifecycle and cleanup guides already contain much of this policy; the missing value is consistent enforcement through the supported creation/closeout entry points. A better prompt helps, but a prompt alone cannot stop another launcher from creating unregistered repositories.

## A bounded next slice

1. Select one backup engine and construct one representative closed recovery package: dirty linked worktree, actual common store, ignored log, pinned binary, external dependency and a junction fixture. Restore independently and compare bytes and required Git objects. Repeat capture once to prove incremental operation. Keep originals.
2. Only where new registry work is actually needed, compare a small SQLite implementation against the planned JSON protocol. Keep one authoritative store and retain the external-operation recovery rules. Do not migrate the existing controller as a prerequisite.
3. After the first independently restored batch, if supervision remains a significant burden, trial one read-only helper job under either Prefect or DBOS, using fake local work before provider spending. Bring this forward only if coordination demonstrably blocks that batch. Verify duplicate submission, restart, cancellation with descendants and the shared heavy-work limit. Stop if it fails to remove net code or operator work.

These can be investigated independently, but they must not become three new platforms required before capture and cleanup can proceed. Continue using reviewed existing commands for the current cleanup slice; these libraries are alternatives for specific missing work. Choose at most one pilot initially. The backup restore proof is the most directly connected to safely reducing the current landfill; the other candidates can wait for the code they would replace to need work. Account setup, first-upload duration and independent restore time are unmeasured. Configuring a backup does not make any original eligible for deletion.

No product was installed or purchased, no source controller was changed, and no data was uploaded during this research. Features, pricing and compatibility were checked against current primary sources and selected local code; no migration or end-to-end product benchmark was performed. There is no defensible hours-saved estimate yet.

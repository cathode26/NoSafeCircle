# Findings

F1. Controller defect: checkouts.lock contention is fatal to the invocation (P2 for the e90670d stack; add it to the Issue #36 FIX AFTER list). Any action that must take `<root>\.assistant-control\checkouts.lock` waits at most 10 s; when a post_crew child launched a second earlier still holds that lock, the action raises `TimeoutError: [Errno 10060] timed out after 10s waiting for exclusive file lock`, the controller records it as `last_error`, releases the graph with status `blocked`, and the CLI exits 1. Evidence in run 2's journal (root -Checkouts-6): `post_crew NSC-1163` 02:37:47.225Z to 02:37:57.228Z after `post_crew NSC-1162` launched at 02:37:46.581Z; then `sync_candidate NSC-1163` at 02:50:47.425Z and `auto_approve NSC-1162` at 02:51:32.893Z, so it hits foreground Source-lane actions as well as launches. The failed action had written nothing; every background child survived, finished and wrote its receipt; a relaunch harvested them. Run 1 avoided it only because Sonnet's setup pass had spread the launches; run 3 avoided it by timing. The mechanism exists unchanged in e90670d (`background_jobs.launch`, `source_update.synchronize_candidate`, `ReviewGate`), so on `main` with `--background-jobs 2 --capacity 2` it is unlikely but possible.

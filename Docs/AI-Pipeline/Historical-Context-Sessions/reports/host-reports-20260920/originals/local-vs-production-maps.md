## 2. How a locally accepted task counts as "done" without a TaskGraph delivery record

- There is no TaskControl delivery record and the accepted task's taskcontrol `derived_state` stays `not_delivered` (docstring of `locally_accepted_task_ids`, `local_rehearsal.py:759-766`).
- Source of truth: `LocalRunContext.locally_accepted_task_ids()` (759) = tasks whose record has `pipeline_stage == "local_candidate_accepted"` and a non-empty `local_source_integrated_commit`. Test `local_dependency_acceptance_test.py:test_context_reports_only_integrated_acceptances` pins this (a record with the stage but no integrated commit does not count).
- Overlay: `overlay_local_acceptance` (1473) rewrites a taskcontrol row whose `task_id` is in that set from any non-error, non-`conformant` state to `LOCAL_ACCEPTED_DEPENDENCY_STATE = "needs_testing"` (1470), adding `local_acceptance: {authority:"local_candidate_accepted", taskcontrol_state:<original>}`. `dispatch_policy.json` lists `needs_testing` in `dependency_dispatch_satisfied_states`, and `dispatch_policy.py:dependencies_dispatch_satisfied` (128) is the single predicate; `dispatch_plan.py` lines ~243-250 label such a dependency `revalidation_debt` and treat it as satisfied.
- Scheduler side: `polling_orchestrator.py:build_poll_dispatch_plan` (1444) wraps the taskcontrol provider in `LocalAcceptanceStateProvider(state_provider, context.locally_accepted_task_ids())` (1508-1514) so `plan_dispatch` sees dependents as eligible. Because the provider also overlays the accepted task's *own* row to `needs_testing`, `dispatch_plan.py:233-238` rejects it as fresh work (`derived_state_not_fresh:needs_testing`); it is additionally excluded because `build_poll_dispatch_plan` adds every task whose local `state in {local_review_ready, blocked, failed}` to `excluded_task_ids` (1467-1470).
- Worker side: `real_workflow.py:observe_goal_state` (187) applies `overlay_local_dependency_states(task, context.locally_accepted_task_ids())` before `_task_ready_for_coordination` (163) calls `dependencies_dispatch_satisfied(task["dependency_states"])`, so the worker's admission agrees with the scheduler (test `test_worker_observation_agrees_with_the_scheduler`). `dependencies_conformant` stays False; strict conformance is never claimed.
- Graph classification: `evaluate_local_graph_state` (1398) treats accepted tasks as terminal because their `state` is still `local_review_ready`; the run reaches classification `local_review_ready` when every record is in that state and nothing is active (1437-1438), which `run_autonomous_graph.py:_run_local_owned` maps to `EXIT_COMPLETE` (line ~811). No `complete` classification and no graph-complete receipt exist locally (`autonomous_graph_run.py:1648-1650` refuses one).
- Dependents that start after acceptance are admitted at the new Source commit: `LocalTaskCheckoutManager._prepare_unlocked` calls `context.admit_task_at_current_source` (`local_rehearsal.py:499`) on first checkout, cloning from `context.source_root` at `context.source_head`, so their checkout contains the accepted work. Tasks already checked out keep their admitted commit (`task_admitted_source`, `crew_manifest_path` 524).

## 3. Where NSC-042 is held and what "local review ready" means

- `production_pipeline.py:_local_manual_review` (37-45) returns True only for `PRESERVED_TASK_ID == "NSC-042"` (`prepare_synthetic_gauntlet.py:57`). - `LocalRunContext.finish` still runs: record `state=local_review_ready`, `pipeline_stage=local_review_ready`, `worker_id`/`lease_id` retained, `result.local_manual_review = True`, no `local_candidate_commit` key; Issue-shaped record moved to `BLOCKED` with `local_status: local_review_ready`.
- Nothing local can move it afterwards: `continue_local_candidate_integrations` only enqueues records with an embedded `local_candidate_commit` (201-203); `build_poll_dispatch_plan` excludes `local_review_ready` tasks; `LocalTaskCheckoutManager._inspect_unlocked` short-circuits with `status=local_review_ready` (line ~86); `_pipeline_status` returns `{"status":"local_review_ready","next_action":"Review the local rehearsal artifacts.","authority":"local_rehearsal_only"}` (`_local_terminal_guidance`, 48-57). It is not in `locally_accepted_task_ids()`, so anything depending on NSC-042 is never dispatch-satisfied locally.
- Meaning of `local_review_ready`: a terminal, lease-retaining record meaning "verified crew output exists; no publication, no delivery, no conformance, no human PASS" (`LOCAL_AUTO_APPROVAL_HANDOFF.md` "Reproduced boundary"; `openai_pipeline.py:_LOCAL_GOAL_AND_RULES` 106-131). There is no local human channel; `evaluate_local_graph_state` comment (1425-1430) states `human_action_required` locally is a deadlock by design. The human "review" of NSC-042 locally is out-of-band inspection of the run root (gauntlet viewer / artifacts); the run itself simply ends `local_review_ready` when all tasks are terminal.
- Two flavours share the same `state`: `pipeline_stage=local_review_ready` (worker finished; manual or auto-accept off, or accepted-but-not-yet-integrated with lease still held) vs `pipeline_stage=local_candidate_accepted` (integrated, lease cleared).

Invariants the code enforces:

- **Hash chains.** `local-manifest.json` and `local-state.json` carry `manifest_sha256`/`state_sha256` (`semantic_sha256`); every state event carries `event_id` = hash of its body and `previous_event_id` (`_save`, `_load_unlocked` 690-705). Candidate receipt: `receipt_sha256`; queue items re-hash their embedded receipt on every load (`LocalCandidateQueue._load`). Crew receipt: `receipt_sha256`; crew result bytes are re-hashed before use (`_verified_pipeline_generated_paths`, `_record_local_provider_usage`).
- **Exact identity at every hop.** `LocalCandidateCommitter.commit` requires scope authority == crew receipt (task, lease, plan, source_head, contract hash); `_verify_local_receipt` and `_recover_committed_candidate` require the checkout HEAD/parent/tree and trailers to match; `_assert_candidate_worker_evidence` requires the durable record's `result` to match the receipt before Source is touched (`assert_local_candidate_ready`, 997); `_verify_recovered_source_commit` requires blob-level equality with the candidate commit.
- **Single bound Source commit, single-child advances.** `rebind_after_local_candidate` requires `HEAD == integrated_commit` and `parents == [self.source_head]`, clean tree; `_require_manifest` requires `source_lineage` to be a single chain ending at `source_commit`; `_accepted_successor_manifest` (466) accepts only a revision that extends the lineage by entries authorized by the run's own `local_candidate_auto_accept`/`local_decomposition_apply` flags, `manifest_revision+1`, `previous_manifest_sha256` matching. Any other manifest change raises "local manifest changed after admission". `evaluate_local_graph_state` requires `source_head` to be the initial commit or an applied/integrated commit.
- **Serial queue.** `LocalCandidateQueue` is single-owner: `claim_next` under `local-candidate-queue.lock`, `settle` requires exact `(owner, lease_epoch)`; one owner `"local-source-integrator"` per run with `lease_epoch = manifest_sha256`; `claimed_for` refuses multiple claims per epoch; `enqueue` refuses a second non-integrated item per task. Source mutation is additionally serialized by `local-candidate-source.lock` and the process-global `_LOCAL_CANDIDATE_SCOPE` ("one local candidate integration at a time", `local_execution_fence.py:121-122`). The scheduler process itself holds `SchedulerLock` (`polling_orchestrator.py:5858`) and, for startup recovery, `provider-runtime-owner.lock` (`local_rehearsal.py:from_root` 316-323).
- **Cross-process window.** During commit-to-revision the marker `decomposition-apply/IN_PROGRESS.json` (`kind:"candidate"`, parent commit/tree, lease, receipt hash) lets other processes (workers calling `assert_current`) wait up to 120 s via `_wait_for_local_application_revision` (406-464) instead of declaring the run stale; the marker is honoured only if it names the exact `local_review_ready` record, lease and receipt hash (432-438).
- **Fence on git.** Inside `local_candidate_integration_scope`, `apply/add/commit` are allowed only on the Source (`scope[1]`), `reset/restore/clean/write-tree` on Source, task checkout or registered scratch clones; every mutating op must be inside the run root (`validate_local_command` 200-330). Hooks are disabled (`core.hooksPath=/dev/null` in `LocalTaskCheckoutManager`).
- **Wake.** `wake_id` is deterministic (`uuid5` over run/task/integrated commit/state revision) so retries coalesce; `notify_local_candidate_accepted` validates 40-hex commit, 64-hex receipt hash, 32-hex wake id; pending wakes survive a missing listener (`_pending_local_candidate_wakes`).
- **Reconciliation on reap.** `_local_review_ready_reconciles` (598) rejects any worker result whose durable record is not one of the two exact accepted shapes; failure marks `failed_child` and stops admissions.

## 4. Sharp edges relevant to tonight

**4a. Comment hash vs trailing newline / edits / duplicates.** `apply_human_result` hashes the body exactly as it received it (`issue_workflow_store.py:3389`). Action path: body is the REST-returned comment text. Local path: body is the composed string from `_pass_comment` (no trailing newline) that was posted with `gh issue comment --body`. The delivery-evidence step later resolves the human authority with `_authoritative_human_validation` (`downstream_determinism.py:140-215`, installed over `DownstreamTaskController._latest_validation_authority` at `:1435-1454`; exercised by `create_delivery_review_draft` `downstream_pipeline.py:707-711` and the accept path `:871`). It accepts `semantic_sha256({"body": body})` or `semantic_sha256({"body": body.strip()})` (comment at `:190-195`: "which may lack the trailing newline GitHub returns from the API") and then requires exactly one matching comment, raising `authoritative human validation comment is missing, duplicated, or changed` otherwise (`:209-212`). Consequences from that code: editing the PASS comment after the Action recorded it (hash changes), posting the identical PASS text twice (e.g., re-posting after a rejection; `pass_and_resume` dedupes only on exact equality, `:571-573`), or any whitespace difference `strip()` does not normalize, breaks delivery evidence even though the Issue is already `agent_ready`. A comment matching the hash but with a different parsed result/commit raises `hash-bound human validation comment does not match its workflow event` (`:196-203`). `_human_validation_artifact` writes `body.strip()` to `human-validation.txt` (`downstream_pipeline.py:1761-1789`).

**4b. ## 3a. Exact conditions under which `human_revalidation_required` fires

1. **As the downstream worker's terminal status** — `mainline_reintegration._patched_terminal_outcome` (`:1401-1441`, installed over `openai_downstream._terminal_outcome` at `:1489`) returns `status="human_revalidation_required"` whenever the observed Issue is `state == human_action_required` and `phase == unity_runtime_validation`. This includes the **first** handoff created by `prepare_post_merge_human_handoff`, not only re-integrations. `run_pipeline_agent._worker_terminal_contract` (`:370-375`) maps it to terminal `human_action_required`, exit 0.
2. **As an action result** — `_integrate_current_main` returns `{"status": "human_revalidation_required", "receipt", "handoff"}` (`:1387-1391`) after it merged main, revalidated, pushed, and published a new handoff. `classify_mainline_drift` hard-codes `human_revalidation_required: True` (`:189-193`); the automation-only shortcut `_advance_automation_only_issue` is never invoked.
3. **When `integrate_current_main` is selected** (any of):
   - `_mainline_status` (`:214-303`) returns `"required"`: Issue `agent_working` by this worker, phase ∈ {`delivery_evidence`, `merge_closeout`}, checkout ready, `task_head` (Issue `head_commit`, or the recovered evidence commit in merge_closeout) ≠ `environment.source_head`, `git merge-base --is-ancestor <source_head> <task_head>` fails, and (in merge_closeout) task head not already in main. `environment.source_head` is the **scheduler controller checkout's HEAD** (`real_observation.py:131`), not `origin/main`. `_patched_next_action` (`:732-744`) and `allowed_actions_for` (`downstream_determinism.py:596-598`) then force the single action `integrate_current_main`.
   - `_guard_current_main_before_pull_request_merge` (`:904-912`) immediately before publication, with a fresh `git fetch origin main` (`_fresh_mainline_status_before_merge` `:828-901`).
   - `publish_with_base_fence` returns `REJECTED_BASE_MOVED` (`downstream_pipeline.py:1544-1549`).
   - `_assert_human_tested_head` raises "origin/main advanced beyond the validated integration; run integrate_current_main" (`mainline_reintegration.py:794-808`, `downstream_determinism.py:1232-1246`) — this rejects the current action; the next observe routes to `integrate_current_main`.
   Inside `_integrate_current_main` the merge proceeds only if the Issue's exact validation authority (`_authoritative_validation`, `downstream_determinism.py:459-463`) is a PASS for `task_head` (or the recovered implementation commit) (`:960-975`); `already_integrated` if main is already an ancestor (`:993-1009`); `blocked` if main already contains the task head, the remote branch moved, the merge conflicts, deterministic validation fails, or the push does not land exactly (`:1010-1036, 1091-1103, 1200-1224, 1252-1280`).

Net: a second human PASS is required exactly when `origin/main` (as seen by the controller source checkout or a fresh fetch) advanced past the human-tested commit between H1 and publication — after another task's publication, for example, because the gate serializes only the *pre-handoff* merge (step 8) and holds during the human wait; it does not stop other tasks from being published while this one waits, since the owner is held by *this* task.

## 3b. Exact conditions under which the gate owner is judged incoherent

`GateAdmission.filter` (`integration_window.py:594-598`):
```
snapshot = pass_service.find(owner["task_id"])
if snapshot is None or not snapshot.valid or snapshot.state is None:
    raise IntegrationGateError("gate owner Issue is missing or incoherent")
```
This runs on **every scheduler pass** in which the gate has an owner, *before* anything else in the filter, using a run-scoped `GhIssueBackend` (`_pass_service` `:559-578`). It has no tolerance for `pending_transition` — contrast queue waiters (`:653-655`, deferred instead of raised) and `list_agent_ready` (`issue_workflow_store.py:3584-3587`, skipped instead of raised).

`find` (`issue_workflow_store.py:1809-1859`) returns `None` when no **open** Issue authored by an authorized actor has title `<TASK>` / `<TASK> —…` or the body marker `<!-- no-safe-circle-task: <TASK> -->` (`_find_candidates` `:1271-1290`), or when the known Issue number is CLOSED and prebound (`:1819-1823`). It raises (not `None`) on ambiguous matches or unreadable Issues.

`snapshot.valid` is `not reasons` (`_snapshot` `:1495`). Reasons are appended for (`:1404-1447`):
- `parse_state` failure or unauthorized Issue author;
- `validate_event_chain` failure (`issue_workflow.py:1885-2044`): duplicate sequences/ids, non-contiguous sequences, broken `previous_event_id`, state/phase chain breaks, `state_version != len(events)`, body state not equal to the final event's `to_state`, contract-hash mismatches;
- automated-evidence repository mismatch;
- **state label mismatch** — the labels on the Issue must be exactly `{STATE_LABELS[state]}`. The human adding `nsc-state:agent-ready` beside `nsc-state:human-action` produces this reason; `_snapshot` classifies it as a `pending_transition` (`:1439-1484`, via `_classify_pending_transition` `:548-605`, only while the label is ≤ 600 s old, `PENDING_TRANSITION_MAX_AGE_SECONDS` `:275`) **but `valid` stays False**.
`snapshot.state is None` when the body has no state block.

`find` retries only the four transient body/comment skew reasons (`_TRANSIENT_RESERVATION_SNAPSHOT_REASONS` `:240-246`, delays `0,1,2,4,8 s` `:239`); any other reason is final (`_snapshot_is_settled` `:1527-1552`).

Consequently, with the gate parked at `awaiting_exact_commit_validation` on task T, the scheduler raises `gate owner Issue is missing or incoherent` on any pass during which T's Issue is (a) closed, (b) label-ahead-of-body (agent-ready label applied, Action not yet converged or converged but GitHub reads not yet consistent), (c) left with a broken event chain, or (d) missing its state block.

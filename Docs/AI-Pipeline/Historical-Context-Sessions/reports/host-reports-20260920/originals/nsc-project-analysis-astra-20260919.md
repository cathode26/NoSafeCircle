This is not a linked Git worktree. Existing owned records preserve edits; unowned destinations are refused. Task-named historical linked worktrees and current AssistantControl task clones must not be conflated. Moving their paths or merely leaving stale records after removal can break preparation, observation and recovery.

Records use fsync then os.replace (checkouts.py:18–25), which protects an individual JSON replacement. It does not make a recursive copy of records, journal, outputs and source into a consistent transaction. A cleanup snapshot needs its own consistency boundary.

Decomposition is a separate provider proposal and deterministic apply lifecycle. decomposition.py:1–7 states the review-only provider boundary; apply_graph_delta.py:1394–1500 actually checks expected HEAD and repeated clean source invariants. A clean textual merge cannot validate allocated task IDs, ID-map entries, resource groups and dependency rewrites. Decomposition Agent notes at agent-state/decomposition-agent.md:216,263 say branch apply/merge Part 2 is deferred and Vincent agreed to wait. These are queue assertions, not implementation proof. Existing source does establish strict apply guards. Do not make new branch-merge semantics a hidden cleanup prerequisite or describe them as available.

## Cleanup already present, and its gaps

The Cleanup Agent has a measured inventory and owner-release ledger, not a completed universal safe-delete mechanism. agent-state/cleanup-agent.md:6–20 records 138 worktrees, unique detached heads, dirty worktrees and seven released clones. It explicitly preserved tmp-ga and review-tmp despite apparent owner release. The queue contains stale assumptions (tools extraction still queued despite physical tools already moved) and demands a task archive decision. Owner silence, age or a folder name is not proof of dispensability.

Existing C:\NSC-History-20260918 move/restore scripts are unsuitable as an assumed recovery foundation. MOVE-NSC-FOLDERS.ps1:68 routes to from-NSC, whereas RESTORE.ps1:53–68 resolves source by top-level Name and falls back to C:\Name. The cleanup guide:167 explicitly stops both bulk move scripts pending a real round trip. MOVE-NSC-FOLDERS.ps1:708–718 tests HEAD ancestry and ordinary porcelain status, neither of which proves all refs, detached heads, ignored logs, nested repositories or object-store dependents are preserved. Lines 875–877 merely warn about moved worktrees. RESTORE.ps1's empty-log-implies-junk rationale (lines 8–15) is not a deletion proof.

Deletion candidates therefore need exact path and Git topology classification: .git directories versus .git files, common dirs, alternate stores, local origins, nested repos, independent refs and detached tips, tracked/dirty/untracked/ignored bytes, reparse targets, operational and hash-bound references. Capture all logs as explicitly required; ordinary git status misses ignored logs. A common object store can serve checkouts beyond the deletion candidate. A surviving clone's local origin can point at a soon-deleted folder even when its own files look safe. A restore needs both byte integrity and the ability to use the recovered objects without the deleted originals.

## Independent conclusion before the execution plan

There is enough existing infrastructure and measured evidence to organize a small careful cleanup in hours. There is not evidence of a ready end-to-end durable cleanup system. Parallel readers and authors can accelerate artifact preparation; they cannot remove the serial need to agree a snapshot, resolve topology, capture, verify remote-only recovery and authorize exact deletions. Keep candidate-specific holds, allow unrelated game work, and retain uncertain sources. A credible plan must distinguish its installed primitives, missing code, current authority and measured execution capacity.

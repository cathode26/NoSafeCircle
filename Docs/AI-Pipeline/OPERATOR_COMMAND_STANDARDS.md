# Operator Command Standards

This document defines the reliability and safety standards for human-run operator commands produced for this repository.

It is operating guidance, not game-design canon and not evidence of repository state.

These rules exist because this project has repeatedly encountered avoidable command failures at the boundary between ChatGPT/Claude/Codex, Windows PowerShell 5.1, Git, GitHub CLI, Docker/Linux, Python, Unity, and multiple concurrent repository checkouts. The goal is not to make commands verbose for their own sake. The goal is to make a command fail clearly, stop safely, recover from partial progress, and avoid making the operator reconstruct state by hand.

Use this document together with:

- `Docs/AI-Pipeline/OPERATOR_COMMAND_TEMPLATE.md` for the canonical substantial-command skeleton;
- `Pipeline/TaskReviewAgent/NativeCommand.ps1` for PowerShell-safe native-process execution;
- `Docs/AI-Pipeline/OPERATOR_FILE_HANDOFF_AND_DOWNLOADS.md` for external files, transcripts, prompts, and human handoffs;
- task-specific runbooks for the actual operation being performed.

The standards below apply to commands generated by humans or agents. They especially apply to commands an agent gives Vincent to paste into PowerShell.

## Normative language

The terms below are intentional:

- **REQUIRED** — use this pattern unless a reviewed task-specific mechanism explicitly replaces it.
- **PROHIBITED** — do not use this pattern in a paste-ready operator command.
- **DISCOURAGED** — the pattern can work, but a safer repository-approved form should normally be used.
- **READ-ONLY** — the command may observe state but must not create or change repository, GitHub, checkout, pipeline, or external durable state.
- **DURABLE MUTATION** — any change that can survive the current PowerShell process, including file edits, commits, refs, pushes, Issues, PRs, claims, checkouts, external artifacts, or long-lived containers.

## 1. Scope: when the full standard applies

A one-line, clearly read-only command such as:

```powershell
git status --short
```

does not need the full command template.

A substantial command **must** follow `OPERATOR_COMMAND_TEMPLATE.md` when it can do any of the following:

- edit, create, move, or delete files;
- stage or commit Git changes;
- create, move, or delete branches, refs, tags, or claims;
- push or merge;
- create or update GitHub Issues or pull requests;
- create, modify, or remove a task checkout;
- run a multi-step delivery or validation workflow that may be resumed after partial success;
- invoke a provider or other long-running external process;
- create an external artifact that later commands depend on.

## 2. Compatibility baseline

### REQUIRED: assume Windows PowerShell 5.1

Unless the operator explicitly requests another shell, paste-ready commands must work in Windows PowerShell 5.1.

### PROHIBITED: Bash-only syntax in PowerShell blocks

Do not emit constructs such as:

```text
< input.txt
VAR=value command
$(command) as Bash command substitution
```

when the block is intended for Windows PowerShell.

PowerShell redirection and expression syntax must be used instead.

### PROHIBITED: PowerShell-7-only syntax without an explicit PowerShell 7 requirement

Do not assume operators such as `&&`, `||`, or other newer-language conveniences are available merely because they work in a modern shell.

### DISCOURAGED: continuation backticks

Avoid PowerShell backtick line continuation when a one-line invocation, array, splat, parenthesized expression, or other natural continuation can express the same command.

A trailing space after a backtick is nearly invisible and changes parsing.

### REQUIRED: keep compound syntax together

An `if` / `elseif` / `else`, `try` / `catch` / `finally`, function definition, loop, or here-string must be delivered as one syntactically complete block. Do not ask the operator to paste dependent syntax fragments separately.

### REQUIRED: separate adjacent commands explicitly

Every executable command must end through a real PowerShell statement boundary: a newline, semicolon when appropriate, closing block, or pipeline boundary.

Do not produce accidental concatenations such as:

```text
git diff --cached --statgit commit ...
git rev-parse HEADgit commit ...
```

A command generator must review the final rendered block, not only the intended logical steps.

### REQUIRED: disambiguate interpolated variables next to punctuation

When punctuation can be parsed as part of a PowerShell variable reference, use explicit interpolation:

```powershell
Write-Host "PR #$($PrNumber): $PrUrl"
```

Do not rely on ambiguous forms such as a bare variable immediately followed by `:`.

### PROHIBITED: `$PSScriptRoot`-dependent parameter defaults

Do not calculate a `param()` default value from `$PSScriptRoot` when evaluation timing can occur before the script-relative value is safely available.

Instead, accept a nullable/empty parameter and resolve the script-relative default after the `param()` block:

```powershell
param(
    [string]$PromptPath
)

if ([string]::IsNullOrWhiteSpace($PromptPath)) {
    $PromptPath = Join-Path $PSScriptRoot "prompt.txt"
}
```

This prevents defaults from collapsing into malformed root-relative paths such as `\prompt.txt`.

## 3. Generated `.ps1` files must parse before execution

If an agent creates a `.ps1` file rather than giving a direct paste-ready block, syntax validation is part of creation.

### REQUIRED: parser preflight

Use the PowerShell parser and stop on any parse error before executing the script.

Conceptually:

```powershell
$Tokens = $null
$Errors = $null
[System.Management.Automation.Language.Parser]::ParseFile(
    $ScriptPath,
    [ref]$Tokens,
    [ref]$Errors
) | Out-Null

if ($Errors.Count -ne 0) {
    throw "Generated PowerShell script did not parse."
}
```

A parser failure means the script did not execute. Do not treat it as a partial runtime failure.

### REQUIRED: use PowerShell-5.1-safe source encoding

Executable source must be ASCII-safe when practical or saved using an encoding Windows PowerShell 5.1 reads correctly. Do not place typographic punctuation or other non-ASCII characters into an encoding that PowerShell 5.1 will misdecode.

Documentation files may remain normal UTF-8; this rule is specifically about executable PowerShell source.

## 4. A standalone command owns its critical state

### REQUIRED: define critical values inside the block

A substantial paste-ready command must establish its own:

- repository root;
- expected repository/origin when remote authority matters;
- work item or task identity;
- expected branch or allowed branch set;
- base/reviewed SHA when applicable;
- expected patch/target SHA when already known;
- exact paths needed by the operation;
- output/log path when external output matters.

Do not require the operator to remember variables from an earlier pasted command.

### PROHIBITED: runnable placeholders

A paste-ready block must not contain values such as:

```text
<PASTE_SHA_HERE>
REPLACE_ME
SET_ME
<path from previous output>
```

Either derive the value programmatically or stop and ask for the missing authority before presenting a runnable block.

### REQUIRED: validate the working directory explicitly

Do not trust the shell's inherited current directory.

A substantial block must validate the expected root with `Test-Path`, then set its working directory explicitly before commands depend on it.

This protects against shells left inside renamed, moved, or deleted checkouts.

### REQUIRED: resolve repository identity from the checkout

When remote state can be mutated, repository authority comes from the actual checkout and its configured remote, not from conversation text or a hard-coded fallback alone.

An expected repository value may be used as an assertion. A mismatch must fail closed.

## 5. Large and quote-heavy payloads belong in files

### REQUIRED: use durable files for large prompts, patches, JSON, or quote-heavy payloads

Do not force long prompts or structured payloads through one giant command-line argument when a UTF-8 file handoff is available.

This avoids:

- Windows command-line length limits;
- PowerShell quoting/here-string mistakes;
- chat/composer size limits;
- accidental prompt corruption;
- unreadable operator commands.

Load a prepared UTF-8 file explicitly, for example:

```powershell
$Prompt = Get-Content -Raw -Encoding UTF8 -LiteralPath $PromptPath
```

Follow `OPERATOR_FILE_HANDOFF_AND_DOWNLOADS.md` for the canonical external run directory and filenames.

### DISCOURAGED: giant inline here-strings for human-transferred prompts

Here-strings are acceptable for short controlled script literals. They are not the default transport for long prompts or documents that the human may need to inspect, upload, reuse, or pass to another process.

## 6. Native executable semantics

Git, Docker, GitHub CLI, Python, Unity command-line tools, Claude/Codex CLIs, and similar programs are native processes from PowerShell's perspective.

### REQUIRED: native success is determined from exit code

Do not infer native failure from stderr output.

Windows PowerShell 5.1 can convert normal native stderr into `ErrorRecord` objects. Docker lifecycle messages, Git warnings, provider live activity, and other healthy output may arrive on stderr.

Use `Pipeline/TaskReviewAgent/NativeCommand.ps1` when applicable, or reproduce its semantics deliberately:

1. preserve the caller's `$ErrorActionPreference`;
2. run the native command without allowing ordinary stderr to become a terminating PowerShell error;
3. capture `$LASTEXITCODE` immediately after the native pipeline;
4. restore the previous error preference;
5. decide success from the documented exit code.

### REQUIRED: every predicate declares allowed exit codes

Many Git commands use nonzero exit codes as data rather than operational failure.

Examples include predicates such as:

```text
git diff --quiet
git show-ref --verify --quiet
git merge-base --is-ancestor
```

For such commands, the wrapper must explicitly allow the documented set, commonly `0` and `1`, and the caller must branch on the returned code.

Do not send every nonzero native exit code through the same generic failure path.

### PROHIBITED: using captured output count as a predicate when stderr can contaminate it

Do not decide whether a file changed by counting arbitrary captured native output. Warnings can enter the capture stream and turn a false result into an apparent true result.

Prefer commands with documented predicate exit codes, or parse structured stdout separately from diagnostics.

### DISCOURAGED: `2>$null` as error handling

Suppressing stderr is not a substitute for interpreting the exit code. It can hide useful diagnostics and does not establish whether the process succeeded.

### REQUIRED: capture `$LASTEXITCODE` immediately

Do not run another native program, helper, or pipeline before saving the exit code that belongs to the command being checked.

## 7. Cross-OS text boundaries

### REQUIRED: normalize multiline payloads before Linux/Docker

PowerShell here-strings and Windows files may contain CRLF. Bash/Linux tools may interpret retained carriage returns as part of command tokens.

Before a multiline textual argument crosses into Linux, normalize:

```powershell
$Normalized = $Value.Replace("`r`n", "`n").Replace("`r", "`n")
```

`Invoke-NscNativeCommand` already does this for its argument list.

### REQUIRED: distinguish host Git authority from container filesystem observations

A Linux container bind-mounted onto a Windows checkout may report line-ending/stat differences that Windows Git does not treat as real content changes.

For the real Windows repository, host Git is authoritative for the final changed-file set unless a task-specific policy explicitly establishes another authority.

Do not let a container report hundreds of CRLF-only changes and automatically widen an implementation scope.

### REQUIRED: structured machine output uses an explicit encoding

When consuming JSON or other structured output from tools such as `gh`, decode/process it as UTF-8 rather than relying on the Windows console code page.

## 8. Automated text editing

Command-generated repository edits require the same fail-closed behavior as code.

### PROHIBITED: unchecked newline-sensitive multiline replacement

Do not mutate a tracked file with a large exact `String.Replace()` whose match depends on unknown CRLF/LF representation.

### Preferred edit order

Use, in order of preference:

1. a parser or structured editor appropriate to the file format;
2. a line-based edit with an exact anchor;
3. a small Python/editor script with explicit assertions;
4. normalized regex/text replacement with an exact expected match count.

### REQUIRED: normalize before textual matching when newline format is relevant

For unstructured text editing, normalize the input before searching multiline content.

### REQUIRED: prove the anchor count before mutation

For an edit intended to hit one location:

```text
0 matches  -> stop
1 match    -> allowed to continue
>1 matches -> stop
```

Do not silently choose the first match.

### REQUIRED: validate file scope immediately after editing

If an operation is authorized to change exactly two files, compare the actual path set to those two exact paths before tests, staging, or commit.

A changed-file count alone is insufficient because two wrong files can still have a count of two.

### REQUIRED: write deterministic text encodings/newlines when the repository cares about them

If a generated editor rewrites a text file, it must preserve or intentionally normalize encoding and newline behavior according to repository conventions. Avoid incidental BOM/newline churn.

## 9. Git mutation safety

### REQUIRED: stage exact paths for bounded work

For reviewed or bounded changes, use exact paths:

```powershell
git add -- path/one path/two
```

Then verify the staged path set.

### PROHIBITED: convenience staging for bounded reviewed work

Do not use these merely to make a patch or commit "pick everything up":

```text
git add .
git add -A
```

They can capture unrelated generated files, Unity churn, logs, or another agent's work.

### REQUIRED: distinguish Git identities by role

Do not overload one variable such as `$ExpectedHead` for several different authority points.

Use explicit concepts such as:

```text
ReviewedBase
PatchCommit
RemoteBranchHead
PullRequestHead
MergeCommit
CurrentMain
```

A command and its final report should make clear which SHA is which.

### REQUIRED: rerunnable mutating commands are state-observing and resume-safe

A command that may be rerun after a commit, push, Issue update, PR creation, or merge must inspect current durable state before deciding the next mutation.

Do **not** assume:

```text
command did not print DONE -> nothing happened
```

An earlier attempt may have committed successfully and failed later.

The base SHA is an authority anchor, not necessarily the only legal current `HEAD` on a resumed operation.

### PROHIBITED: blind destructive recovery

Do not automatically use:

```text
git reset --hard
git clean -fd
force push
forced branch-ref movement
```

as generic recovery.

If destructive recovery is genuinely required, it must be an explicit reviewed operation with exact state checks and a clear explanation of what will be discarded.

### PROHIBITED: blanket restore of unrelated changes

When a known generated/stat-only file needs restoration, prove the exact file is safe to restore. Do not restore a whole directory or tree simply to make `git status` clean.

## 10. Path and checkout safety

### REQUIRED: use path APIs, not string slicing

Do not derive repository-relative paths by subtracting string lengths or slicing absolute path strings. Windows may expose equivalent paths using different textual forms, including expanded versus short 8.3 names.

Use `Join-Path`, `Path.GetFullPath`, Python `pathlib`, Git-relative paths, or equivalent path-aware operations.

### REQUIRED: treat absolute and repository-relative paths as different concepts

Validate whether a value is absolute before joining it with a repository root. Do not accidentally prepend the repository root to an already-absolute path.

### REQUIRED: use deliberately short checkout/temp roots for deep repositories

Windows path-length limits can break validation clones even when the repository itself is valid.

Use established short roots such as `C:\NSC\NSC` and short temp roots for disposable clones.

When Git must materialize long paths on Windows, use an operation-scoped `core.longpaths` configuration as needed rather than assuming the default checkout will succeed.

### PROHIBITED: global `safe.directory` as a generic fix

If a disposable clone triggers Git ownership protection because it was cloned from an inappropriate local source, correct the clone/source strategy. Do not broadly weaken Git ownership checks through global configuration.

Prefer a trusted remote origin for disposable verification clones when repository policy expects remote identity.

## 11. Split deterministic setup from expensive provider execution

For normal provider-backed work, deterministic preparation and provider execution are separate phases unless an established pipeline entry point intentionally combines them.

The preferred operator flow is:

```text
PHASE 1
    repository/task/checkout preparation
    deterministic validation
    print READY

PHASE 2
    recheck prepared state
    invoke Claude/Codex/provider
    stream activity
    persist transcript
    print handoff/result
```

This prevents a provider call from starting merely because setup succeeded and makes retries cheaper and easier to diagnose.

Follow the fuller rules in `OPERATOR_FILE_HANDOFF_AND_DOWNLOADS.md`.

## 12. Long-running process visibility and lifecycle

### REQUIRED: visibly announce long-running work

Use concise stage markers such as:

```text
[START]
[VERIFY]
[READ]
[PLAN]
[WORK]
[AGENT]
[TOOL]
[TEST]
[PASS]
[RETRY]
[BLOCKED]
[DONE]
```

The operator should be able to tell whether a process is preparing, waiting, invoking an agent, testing, retrying a known transient condition, or finished.

### REQUIRED: provide a heartbeat or incremental activity for potentially long silent operations

A long-running provider invocation must not appear frozen for tens of minutes when useful activity can be surfaced.

For Python-driven processes, use unbuffered output where needed. For provider CLIs, use the established streaming transport rather than assuming Python unbuffering alone exposes provider activity.

### REQUIRED: record verbose output to a known path when it may be needed later

Display concise live output and persist a transcript/log according to `OPERATOR_FILE_HANDOFF_AND_DOWNLOADS.md`.

### PROHIBITED: open-ended interactive shells for bounded automation

Do not launch an interactive shell or provider session and leave it running indefinitely when the intended operation is a bounded one-shot command.

Automation should launch the actual bounded process and have a clear lifecycle.

### REQUIRED: understand automatic cleanup before issuing cleanup commands

If a container was started with automatic removal, its disappearance after stop/exit may be expected. Do not interpret a later "no such container" cleanup response as proof the original operation failed.

## 13. Output volume is part of command correctness

### REQUIRED: scope exploratory searches

Search commands should prefer:

- a relevant directory;
- filenames first;
- a bounded result count;
- exclusions for generated/raw historical data when appropriate;
- a saved log when complete detail is required.

### DISCOURAGED: dumping an entire repository search into the terminal

A command that returns tens of thousands of lines is operationally poor even if technically correct. It can hide the relevant result and make human handoff harder.

### REQUIRED: final status is concise and authoritative

A successful substantial command should end with a clear summary such as:

```text
[DONE] <operation>
[STATE] Repository: ...
[STATE] Branch: ...
[STATE] Base: ...
[STATE] Patch/Result: ...
[STATE] Remote/PR/Merge: ...
[STATE] Working tree: CLEAN
[NEXT] <one concrete next action>
```

Only print fields that actually apply, but do not make the operator infer success from preceding tool noise.

## 14. Failure classification and recovery

A command standard is incomplete if it only defines the happy path.

Every substantial operation should allow the operator or next agent to classify a stop into one of these categories.

### Parse failure

The PowerShell block/file did not parse.

Expected recovery:

- assume no block execution occurred;
- correct the syntax/encoding;
- rerun only after parser preflight.

### Precondition failure

Repository/path/branch/authority/cleanliness checks deliberately stopped the operation before its intended mutation.

Expected recovery:

- observe why the precondition is false;
- do not force the expected state;
- revise the plan or expected authority.

### Expected predicate false

A command returned a documented nonzero value representing `false`, `not present`, `not ancestor`, or another normal negative predicate.

Expected recovery:

- treat it as state data;
- do not report it as an operational command failure.

### Runtime failure before durable mutation

Tools executed, but no durable mutation crossed its success boundary.

Expected recovery:

- diagnose the operational error;
- retry only when safe.

### Partial mutation

One or more durable steps succeeded before a later step failed.

Examples include:

```text
commit created, push failed
push succeeded, PR creation failed
PR exists, CI wait failed
merge succeeded, local main update failed
file written, later validation failed
```

Expected recovery:

- do not blindly rerun the original command;
- re-read current Git/GitHub/filesystem state;
- verify and reuse successful durable work;
- continue from the next missing step.

### Transient operational failure

A failure is retryable only when positively classified as transient by a narrow signature or typed outcome.

Do not convert arbitrary operational failures into contention/retry behavior.

Examples of acceptable narrow retry handling include a known temporary Windows bare-repository fixture failure that production correctly classifies as an operational error.

### Recovery output must not mask the original error

A `catch`/recovery block must be more defensive than the main work. It may execute before helpers, repository state, or external tools are available.

Recovery inspection must therefore:

- check that paths/helpers exist before using them;
- best-effort print branch/HEAD/tree state;
- preserve the original exception as the final thrown error.

## 15. State and mutation ledgers

A mutation ledger is recommended for multi-boundary runners.

Example conceptual fields:

```text
FilesModified
CommitCreated
BranchPushed
IssueUpdated
PullRequestCreated
MergeCompleted
```

Set a field only after the durable result has been independently re-observed.

The ledger is not authority. It exists to make partial progress legible in terminal output. Current Git, GitHub, TaskGraph, files, and deterministic tests remain authoritative.

## 16. External files and handoffs

Human-facing prompts, logs, patches, review bundles, and temporary handoff files should follow `OPERATOR_FILE_HANDOFF_AND_DOWNLOADS.md`.

Important command-construction implications include:

- write to the final intended path rather than creating a file somewhere arbitrary and asking the operator to move it;
- use a fresh run directory/ID for no-overwrite tools;
- do not put pipeline-owned or hash-bound evidence into Downloads merely for convenience;
- avoid giant inline prompts when a durable UTF-8 prompt file is safer;
- verify required files exist before invoking a tool that depends on them.

## 17. Repository editing and validation boundaries

### REQUIRED: validate before staging and again after staging when appropriate

A bounded code/document change should normally establish:

1. actual changed path set;
2. targeted tests;
3. broader deterministic validation required by the affected area;
4. whitespace check;
5. exact staged path set;
6. staged whitespace check.

### REQUIRED: distinguish a command failure from a product/test failure

If `python some_test.py` runs successfully and reports an assertion failure, the operator command itself may be correct while the repository/tested behavior is wrong.

Do not "fix the command" merely because a deterministic validation exposed a genuine repository defect.

Conversely, a parser, path, encoding, invocation, or native-process handling error is a command-construction failure and should be corrected without changing production behavior to accommodate the bad command.

## 18. Do / do not quick reference

| Do | Do not |
| --- | --- |
| Assume Windows PowerShell 5.1 | Use Bash `< file` redirection in a PowerShell block |
| Deliver complete syntactic blocks | Send `else`, `catch`, or dependent syntax as a later fragment |
| Separate adjacent commands explicitly | Allow command strings to concatenate accidentally |
| Resolve `$PSScriptRoot` defaults after `param()` | Depend on `$PSScriptRoot` in parameter-default evaluation |
| Define critical state inside the block | Depend on variables from a prior paste |
| Use files for large/quote-heavy payloads | Put giant prompts into fragile command-line arguments |
| Validate root, repo, branch, authority, and tree | Trust the inherited current directory |
| Use native exit codes | Treat any stderr as failure |
| Declare allowed predicate exit codes | Treat Git predicate exit `1` as automatically broken |
| Normalize CRLF before Linux | Pass raw Windows multiline text into Bash/Docker |
| Use structured/line-based exact-count edits | Use unchecked newline-sensitive multiline `.Replace()` |
| Compare exact changed paths | Trust only a changed-file count |
| Stage exact approved paths | Use `git add .` or `git add -A` for bounded work |
| Observe current durable state before resume | Assume no `[DONE]` means nothing happened |
| Give base/patch/remote/merge SHAs distinct names | Reuse a generic `$ExpectedHead` for every state |
| Use path APIs | Derive paths through string slicing |
| Use short canonical Windows roots | Create unnecessarily deep temp clones |
| Stream progress and save logs | Leave long-running commands apparently frozen |
| Launch bounded provider processes | Leave interactive shells/containers alive indefinitely |
| Print a concise final/recovery state | Make the operator infer what happened from raw output |

## 19. Agent pre-handoff review checklist

Before an agent gives Vincent a substantial paste-ready command, the agent must review the command against this checklist.

### Syntax and compatibility

- Is the block Windows PowerShell 5.1 compatible?
- Is every compound construct syntactically complete?
- Are executable commands clearly separated rather than accidentally concatenated?
- Are there any fragile continuation backticks that can be removed?
- Are variable interpolations unambiguous around punctuation?
- Are `$PSScriptRoot`-dependent defaults resolved after `param()`?
- If this is a generated `.ps1`, has it been parser-preflighted?

### Identity and state

- Does the block establish its own root and critical state?
- Are there any literal placeholders?
- Is repository identity verified from the checkout when remote state matters?
- Does it validate the correct branch or allowed branch set?
- Does it distinguish base, patch, remote head, PR head, merge commit, and current main where applicable?

### Resume behavior

- Could an earlier run have partially succeeded?
- If yes, does the block observe current durable state before mutating?
- Will an already-created commit/branch/PR be reused rather than duplicated?
- Does failure output say what might already have happened?

### Native commands

- Is success determined from exit codes rather than stderr?
- Are expected predicate exit codes explicitly allowed?
- Is `$LASTEXITCODE` captured immediately when not using the shared wrapper?
- Can stderr contaminate any captured value used as data?

### Editing and Git scope

- Are text-edit anchors exact-count checked?
- Are line endings normalized before multiline textual matching?
- Is actual changed-file scope compared to exact expected paths?
- Is staging limited to exact paths?
- Are destructive Git recovery commands absent unless explicitly reviewed?

### Cross-platform and paths

- Are multiline Linux/Docker payloads LF-normalized?
- Are host/container paths kept distinct?
- Are path operations path-aware rather than string arithmetic?
- Are Windows path-length constraints relevant to any clone/temp operation?

### Payload and human usability

- Should a large or quote-heavy argument be a file instead?
- Will long-running work visibly show progress or heartbeat?
- Is verbose output saved to a useful handoff path if needed?
- Is output bounded enough to remain readable?
- Does success end with `[DONE]` and exact resulting state?
- Does failure preserve the original error and print recovery state?

If the answer to a relevant checklist item is "no", correct the command before presenting it.

## 20. Machine-enforceable subset

Not every rule above should become a linter. Mechanical checks should be limited to high-confidence failure patterns.

Good candidates include:

- parse repository-owned operator `.ps1` scripts with the PowerShell parser;
- regression-test `Invoke-NscNativeCommand` behavior;
- ensure `AGENTS.md` and `CLAUDE.md` point agents to this standard/template;
- detect literal paste-ready placeholder markers in canonical operator scripts;
- detect obvious Bash input-redirection patterns in repository-owned Windows PowerShell runners;
- detect use of `$PSScriptRoot` in parameter-default expressions where evaluation timing can produce an invalid path;
- smoke-test any reusable repository file-edit helper against both CRLF and LF inputs.

Do not build a broad style linter that generates false positives or becomes another source of ceremony. The purpose of mechanical enforcement is to prevent known expensive failures.

## 21. Core principle

A good operator command does not merely work when executed once under ideal conditions.

It should make these questions answerable from the command and its output:

```text
Where am I?
What repository am I operating on?
What authority did I verify?
What has already happened?
What is the next missing mutation?
What exactly changed?
Did the native tools actually succeed?
What deterministic validation passed?
If the command stopped, did anything durable already happen?
Is rerunning safe, or must current state be observed first?
What should happen next?
```

The repository should prefer a slightly longer command that answers those questions over a shorter command that leaves state implicit.

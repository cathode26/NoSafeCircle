# Provider-neutral AgentRuntime

This Stage 3A foundation extracts the reusable orchestration ideas demonstrated by Assignment 3: fresh bounded invocations, explicit request/result handoffs, semantic capability limits, structured output, normalized failures, and immutable run artifacts. `AgentCrew/` and `Assignment6GER/` remain unchanged historical coursework evidence; this package neither imports nor retrofits them.

`AgentRequest` describes task identity, role, context, semantic capabilities, write policy, output shape, capability-class selection, and budgets. Its task contract path is bound to `Tasks/<task_id>.yaml`. `AgentResult` describes only an invocation outcome and provider/agent claims. Neither contract establishes delivery, conformance, readiness, authorization, integration, repository changes, command execution, or test success. Those remain decisions for deterministic repository, test, and evidence systems.

All retained request, result, and runtime-configuration JSON values are recursively validated and frozen. Runtime configuration invariants apply equally to direct construction, dictionaries, and strict JSON loading. Only exact built-in JSON null, booleans, integers, finite numbers, valid UTF-8 strings, lists/tuples, dictionaries, and the runtime's own frozen mapping proxies are accepted. Polymorphic container and text subclasses are rejected so provider callbacks cannot run during validation or make publication disagree with the validated snapshot. Cycles and nesting deeper than the conservative 64-container limit are rejected deterministically. `to_dict()` methods return detached mutable copies. The runner accepts only the exact `AgentRequest`, `RuntimeConfiguration`, and `ProviderInvocationResponse` types; requests additionally require exact `TaskContractIdentity`, `WriteBoundaries`, and `Budgets`, while results require exact `Usage`. Base serializers are called non-polymorphically, preventing subclass serialization or response-container overrides at these trust boundaries.

Identifiers use conservative lowercase ASCII forms: run IDs are 1–64 character lowercase alphanumeric/hyphen slugs, while roles and configuration keys begin with a lowercase letter and use lowercase letters, digits, underscores, and separated hyphens. Every serialized operational string must be UTF-8 encodable. Repository paths are already-normalized, relative POSIX paths and additionally reject surrogates, NUL, ASCII controls, DEL, line breaks, tabs, Windows-forbidden characters, alternate-data-stream colons, trailing dots/spaces, and reserved Windows device names. Write-boundary components are compared conservatively and case-insensitively while remaining component-aware; denied boundaries override allowed ones. Budget maxima are 1,000 turns, 86,400 seconds, and 10,000,000 tokens.

Provider adapters expose an identifier, accept the common request plus a configured concrete model, return structured output and raw log text separately, and normalize provider failures. They translate invocation mechanics only. They may never write task/evidence/readiness state or declare delivery, conformance, readiness, or authorization. Future live-provider adapters must pass the same contract suite.

`ProviderOutputInvalid` represents provider output from which an adapter could not produce a structured-output candidate. `AgentRunner` normalizes it to `schema_error`. This is distinct from a successfully parsed candidate that the runner later rejects through central schema validation, although both outcomes normalize to `schema_error`. Exact provider raw output is retained in `provider.log` when it is valid. `ProviderOutputInvalid` establishes no deterministic correctness, delivery, conformance, readiness, authorization, approval, integration, or test-success authority.

`FakeProvider` is deterministic and performs no network, command, version-control, engine, or repository access. It exercises success, provider failure, invalid provider output, timeout, permission denial, budget exhaustion, and centrally detected schema failure.

Each caller-supplied run root receives a uniquely and atomically created `<run_id>/` containing canonical `request.json`, `provider.log`, and `result.json`. JSON artifacts use strict finite JSON, deterministic key ordering, UTF-8 bytes, LF line endings, and one trailing LF. `provider.log` is the provider's exact raw text and is not decorated with runtime diagnostics. Each file is written and fsynced as a temporary file, then atomically hard-linked into place only if its destination does not exist; failed publication cleans its temporary file and cannot overwrite existing bytes. Existing run directories are never reused. A run directory is an audit artifact, not evidence of correctness.

After a valid request exists, the runner creates the run directory and publishes `request.json` before resolving provider configuration. Unknown configurations, unavailable configured providers, and missing capability mappings therefore produce a preserved failed `result.json` classified as `invalid_request` without invoking a provider. Provider and model are null only when this pre-invocation selection did not succeed; post-selection failures retain the selected values.

Every failed `AgentResult` has a non-whitespace, non-authoritative `failure_message` and must keep `structured_output` null so rejected output cannot appear accepted; successful results leave the diagnostic null or empty. This diagnostic preserves configuration, provider-exception, schema-validation, and rejected-metadata details. It never establishes delivery, conformance, readiness, authorization, test success, or approval. Provider invocation failures and structured-output validation are normalized separately: unexpected ordinary provider exceptions are `internal_error`, while invalid structured JSON or schema mismatch is `schema_error`. Provider responses are field-snapshotted exactly once after their exact-type check. Structured output is immediately detached and frozen, and that same snapshot is both schema-validated and retained. Valid usage and execution/change/test claims survive a post-invocation `schema_error`, while rejected structured output remains null. Invalid raw logs are replaced by an empty log and a safe diagnostic; malformed exception text cannot block artifact publication. Process-control exceptions are not swallowed.

Structured output supports only these JSON Schema features: the object, array, string, integer, number, boolean, and null types; `properties`; `required`; boolean `additionalProperties`; `items`; and `enum`. Unknown keywords fail closed. The runner—not an adapter—validates successful output.

`AgentRequest` remains schema 1.0 with its existing required positive integer `turn_limit`. This change does not implement live Claude or Codex adapters.

Stage 3A deliberately has no live provider, fallback, crew roles/prompts, engine execution, GER integration, task selection, version-control workflow, TaskGraph evidence creation, conformance/readiness derivation, or dispatch authorization.

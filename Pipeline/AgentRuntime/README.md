# Provider-neutral AgentRuntime

This runtime foundation extracts the reusable orchestration ideas demonstrated by Assignment 3: fresh bounded invocations, explicit request/result handoffs, semantic capability limits, structured output, normalized failures, and immutable run artifacts. `AgentCrew/` and `Assignment6GER/` remain unchanged historical coursework evidence; this package neither imports nor retrofits them.

`AgentInvocationRequest` describes one generic bounded invocation: run identity, role, prompt, repository context, semantic capabilities, write policy, output shape, capability-class selection, budgets, and provider configuration. It has no No Safe Circle task identity and no dependency on `Tasks/*.yaml`. `AgentResult` describes only an invocation outcome and provider/agent claims. Task identity belongs to `Pipeline/TaskExecution`; delivery, conformance, readiness, authorization, integration, repository changes, command execution, and test success remain decisions for higher deterministic repository, test, and evidence systems.

All retained request, result, and runtime-configuration JSON values are recursively validated and frozen. Runtime configuration invariants apply equally to direct construction, dictionaries, and strict JSON loading. Only exact built-in JSON null, booleans, integers, finite numbers, valid UTF-8 strings, lists/tuples, dictionaries, and the runtime's own frozen mapping proxies are accepted. Polymorphic container and text subclasses are rejected so provider callbacks cannot run during validation or make publication disagree with the validated snapshot. Cycles and nesting deeper than the conservative 64-container limit are rejected deterministically. `to_dict()` methods return detached mutable copies. The runner accepts only the exact `AgentInvocationRequest`, `RuntimeConfiguration`, and `ProviderInvocationResponse` types; requests additionally require exact `WriteBoundaries` and `Budgets`, while results require exact `Usage`. Base serializers are called non-polymorphically, preventing subclass serialization or response-container overrides at these trust boundaries.

Identifiers use conservative lowercase ASCII forms: run IDs are 1–64 character lowercase alphanumeric/hyphen slugs, while roles and configuration keys begin with a lowercase letter and use lowercase letters, digits, underscores, and separated hyphens. Every serialized operational string must be UTF-8 encodable. Repository paths are already-normalized, relative POSIX paths and additionally reject surrogates, NUL, ASCII controls, DEL, line breaks, tabs, Windows-forbidden characters, alternate-data-stream colons, trailing dots/spaces, and reserved Windows device names. Write-boundary components are compared conservatively and case-insensitively while remaining component-aware; denied boundaries override allowed ones. Budget maxima are 1,000 turns, 86,400 seconds, and 10,000,000 tokens.

Provider adapters expose an identifier, accept the common request plus a configured concrete model, return structured output and raw log text separately, and normalize provider failures. They translate invocation mechanics only. They may never write task/evidence/readiness state or declare delivery, conformance, readiness, or authorization. Live-provider adapters must pass the same contract suite.

`ProviderOutputInvalid` represents provider output from which an adapter could not produce a structured-output candidate. `AgentRunner` normalizes it to `schema_error`. This is distinct from a successfully parsed candidate that the runner later rejects through central schema validation, although both outcomes normalize to `schema_error`. `ProviderRequestRejected` represents a provider that cannot safely honor a selected request policy and normalizes to `invalid_request` after provider/model selection. Exact provider raw output is retained in `provider.log` when it is valid. Neither exception establishes deterministic correctness, delivery, conformance, readiness, authorization, approval, integration, or test-success authority.

`FakeProvider` is deterministic and performs no network, command, version-control, engine, or repository access. It exercises success, provider failure, invalid provider output, timeout, permission denial, budget exhaustion, and centrally detected schema failure.

`ClaudeCodeProvider` supports the empty capability set, `repository_read`, `repository_search`, their read/search combination, and the exact Stage 5A write combination `repository_read + repository_search + repository_write`. Empty-capability invocations retain the Stage 4B behavior: a new empty temporary directory outside the repository with no tools. Read/search invocations run against the actual source repository root (`/workspace` in Docker): `repository_read` exposes native `Read`, while `repository_search` exposes native `Glob` and `Grep`. Write additionally exposes `Edit` and `Write` only when the provider is constructed with `externally_isolated_writable_repository=True` and a concrete existing directory filesystem-disjoint from the real source checkout (neither equal to it, below it, nor an ancestor containing it). `Bash`, `NotebookEdit`, web tools, approved command execution, and every non-null token limit remain rejected or unavailable.

Nonempty `context_paths` remain invalid without a repository capability. With a repository capability they are accepted as validated repository-relative invocation hints and added to a generated repository-context section in the effective provider prompt without mutating the `AgentInvocationRequest`. They are guidance, not a hardened read allowlist. This trusted single-user boundary intentionally prioritizes useful access to the current working tree; ADR-038 records the accepted limited risk.

Claude receives the exact concrete configured model with no alias or fallback, native `--max-turns` equal to the request's required positive `turn_limit`, and the independent external hard `timeout_seconds` enforced by the shared subprocess transport. The prompt travels through stdin, while the compact output schema and tool policy travel as direct argv elements with `shell=False`. Every invocation passes `--setting-sources user,project`, intentionally excluding the `local` source and repository `.claude/settings.local.json` from bounded production execution. Provider tool authority comes from AgentRuntime's explicit `--tools`, `--allowedTools`, and `--disallowedTools` policy, not machine-local permission allowances. `--tools` is the exact available built-in tool surface; for every nonempty capability profile, list-style `--allowedTools` separately pre-approves exactly that same surface under `dontAsk`. Stage 5A write calls therefore make `Edit` and `Write` both available and explicitly pre-approved. Empty-capability calls retain `--tools ""` and omit `--allowedTools`. Explicit denials remain profile-specific, and `Bash` is always unavailable and denied. The shared standard-library transport captures stdout and stderr concurrently through `communicate`, creates a new process group/session, terminates the group on timeout with bounded cleanup, and preserves available partial output. Deterministic adapter and AgentRunner integration tests inject a fake process runner and never launch Claude. The opt-in `tests/claude_repository_read_search_live_smoke.py` requires `NSC_RUN_CLAUDE_REPOSITORY_SMOKE=1`; normal deterministic runs skip live Claude access.

Claude stdout is decoded strictly as UTF-8 and retained exactly as `provider.log`. A successful response must be one JSON result envelope with exact built-in status metadata: `type=result`, `is_error=false`, `subtype=success`, `terminal_reason=completed`, and a present `structured_output`; `stop_reason=tool_use` is acceptable. Missing or malformed status or permission-denial metadata is `ProviderOutputInvalid`. A nonempty, exact-list `permission_denials`, other well-formed unsuccessful result envelopes, and nonzero exits are provider failures. `ProviderTransportError` covers local process/transcript failures, invalid usage metadata, and unexpected stderr on a zero exit, and `AgentRunner` normalizes it to `internal_error` while retaining any valid exact raw log. Timeouts remain `timeout` and retain valid partial stdout.

Normalized Claude usage prefers all `modelUsage` entries, including cache-read and cache-creation input tokens, and otherwise falls back conservatively to top-level `usage`. An explicitly present empty `modelUsage` object and malformed, negative, boolean, non-finite, or inconsistent usage fail closed as transport errors.

Each caller-supplied run root receives a uniquely and atomically created `<run_id>/` containing canonical `request.json`, `provider.log`, and `result.json`. JSON artifacts use strict finite JSON, deterministic key ordering, UTF-8 bytes, LF line endings, and one trailing LF. `provider.log` is the provider's exact raw text and is not decorated with runtime diagnostics. Each file is written and fsynced as a temporary file, then atomically hard-linked into place only if its destination does not exist; failed publication cleans its temporary file and cannot overwrite existing bytes. Existing run directories are never reused. A run directory is an audit artifact, not evidence of correctness.

After a valid request exists, the runner creates the run directory and publishes `request.json` before resolving provider configuration. Unknown configurations, unavailable configured providers, and missing capability mappings therefore produce a preserved failed `result.json` classified as `invalid_request` without invoking a provider. Provider and model are null only when this pre-invocation selection did not succeed; post-selection failures retain the selected values.

Every failed `AgentResult` has a non-whitespace, non-authoritative `failure_message` and must keep `structured_output` null so rejected output cannot appear accepted; successful results leave the diagnostic null or empty. This diagnostic preserves configuration, provider-exception, schema-validation, and rejected-metadata details. It never establishes delivery, conformance, readiness, authorization, test success, or approval. Provider invocation failures and structured-output validation are normalized separately: unexpected ordinary provider exceptions are `internal_error`, while invalid structured JSON or schema mismatch is `schema_error`. Provider responses are field-snapshotted exactly once after their exact-type check. Structured output is immediately detached and frozen, and that same snapshot is both schema-validated and retained. Valid usage and execution/change/test claims survive a post-invocation `schema_error`, while rejected structured output remains null. Invalid raw logs are replaced by an empty log and a safe diagnostic; malformed exception text cannot block artifact publication. Process-control exceptions are not swallowed.

`provider_sessions.py` adds an opt-in, provider-neutral persistent-session contract so a pooled worker can keep its authenticated provider conversation resumable between compatible assignments. It models identity only: it is not a running subprocess, a session store, a scheduler, or a pooling policy. A caller that supplies no binding stays exactly ephemeral, so architect, decomposition, reconciliation, ArchitectureReview, and every other current consumer is unchanged.

`ProviderSessionBinding` names one provider, one role, one mode (`start` or `resume`), and one exact lowercase canonical RFC 4122 UUID. Whole-value validation rejects `last`, `--last`, a display or thread name, a search term, an empty value, a partial or uppercase ID, braced and URN spellings, and the nil UUID sentinel, and it refuses a resume with no identity at all — all before any subprocess exists. `compatibility_key()` binds provider and role, so a future scheduler cannot hand a Claude conversation to Codex or resume an Implementer conversation as a Validator; the adapters enforce the same two facts themselves. `ProviderSessionLedger` is a write-once sink for the identity one invocation actually confirmed, which keeps `AgentInvocationRequest`, `AgentResult`, `request.json`, and `result.json` byte-identical for a session-enabled run.

Claude names the conversation, so a persistent invocation supplies the exact UUID: a start passes `--session-id <uuid>` and a resume passes `--resume <uuid>`. The two are mutually exclusive, `--no-session-persistence` is dropped only for a persistent invocation, and `--resume` is never emitted bare because a bare `--resume` opens the CLI's interactive picker. The terminal stream-json result envelope's `session_id` is then required to equal the bound UUID; a missing or mismatched identity is `ProviderOutputInvalid` even on exit `0`.

Codex names the conversation itself, so a persistent start binds no ID, omits `--ephemeral`, and adopts the exact UUID from the single pinned `thread.started` `thread_id` event; missing, malformed, duplicated, and contradictory session events all fail closed. A resume uses `codex exec resume <exact uuid>` and never `--last`. `codex exec resume` does not accept `--sandbox`, so the `--sandbox danger-full-access` policy this adapter pins at start cannot be reproduced there; a resume is therefore refused with `CODEX_RESUME_SANDBOX_BLOCKER` unless the operator supplies a verified `resume_sandbox_argument` reproducing that exact policy through an option resume does accept. Resuming under a silently different sandbox policy is never done.

Every invocation, including a resume, still carries its own repository root, model, output schema, capabilities, allowed and denied write paths, task prompt, and turn/timeout budgets; remembered context never widens current authority. `RESUMED_AUTHORITY_NOTICE` leads a resumed prompt and states that every previous task and write authorization in that conversation has expired. Post-run deterministic changed-path validation is unchanged and remains the authority.

Structured output supports only these JSON Schema features: the object, array, string, integer, number, boolean, and null types; `properties`; `required`; boolean `additionalProperties`; `items`; `enum`; and finite numeric `minimum`/`maximum` on integer or number schemas. Unknown keywords fail closed. The runner—not an adapter—validates successful output.

`OpenAICodexProvider` supports empty capability, repository read, repository search, combined read/search, and the exact Stage 5A write combination `repository_read + repository_search + repository_write`. Read/search requires `externally_enforced_read_only_repository=True`; write instead requires the mutually exclusive `externally_isolated_writable_repository=True` profile and an existing repository root filesystem-disjoint from the real source checkout: neither equal to it, below it, nor an ancestor containing it. Empty-capability requests use a temporary directory outside the repository. It forwards the selected concrete model, sends prompts by stdin, preserves exact JSONL stdout, parses the final-output file, uses the last completed-turn usage event, and enforces `min(timeout_seconds, turn_limit * 30)`. ArchitectureReview supplies only the external Docker read-only profile. Approved command execution, non-null token limits, fallback, and production role orchestration remain unsupported.

Stage 5A enables provider write mechanics only. The exact immutable `WriteBoundaries` are serialized into provider prompts, where they remain semantic policy rather than native path-level enforcement. The writable workspace is disposable and untrusted: `claimed_changed_paths` remains a provider claim, and a future higher-level TaskExecution/ExecutionCrew layer must compare the actual Git diff with `request.write_boundaries`. AgentRuntime does not run Git diff/status, decide delivery or conformance, execute Unity, authorize readiness/dispatch, or commit/merge. The opt-in live smokes construct and verify temporary repositories filesystem-disjoint from the real source checkout—neither equal to it, below it, nor an ancestor containing it—and require the real source mount to be read-only. Run them through the existing read-only-source services:

```bash
docker compose run --rm -T -e NSC_RUN_CLAUDE_WRITE_SMOKE=1 claude-review python3 Pipeline/AgentRuntime/tests/claude_repository_write_live_smoke.py
docker compose run --rm -T -e NSC_RUN_OPENAI_CODEX_WRITE_SMOKE=1 codex-review python3 Pipeline/AgentRuntime/tests/openai_codex_repository_write_live_smoke.py
```

ArchitectureReview is an active generic-runtime consumer for both providers: `architecture_review_claude.py` selects `ClaudeCodeProvider`, and `architecture_review_codex.py` selects `OpenAICodexProvider`. Each invocation produces `request.json`, `provider.log`, and `result.json` beneath its provider-owned ArchitectureReview run. Both integrations retain the same eight shared reviewer roles and independent `outputs/claude/` or `outputs/codex/` provenance; comparison and dual-provider launch orchestration are not implemented.

The runtime still has no crew roles/prompts, engine execution, GER integration, task selection, version-control workflow, TaskGraph evidence creation, conformance/readiness derivation, or dispatch authorization.
